# ReadLead — คำถามตั้งต้นและจุดเสี่ยงสำหรับคุยกับลูกค้า

เอกสารนี้ใช้คุยช่วงแรกก่อนตีราคาและล็อก scope ไม่จำเป็นต้องถามทุกข้อในครั้งเดียว แต่ควรได้คำตอบของห้าคำถามหลักก่อนเริ่มออกแบบระบบ

## เกริ่นเรื่องขอบเขตงาน

> พื้นฐานผมทำงานฝั่ง Frontend เป็นหลักครับ แต่โปรเจกต์ ReadLead มีงาน backend อยู่ด้วยพอสมควร เช่น การดึงเนื้อหาจาก URL, เชื่อม AI สำหรับแปล, เก็บ glossary, จัดการเครดิต, login และ payment
>
> ส่วนนี้เราดูแลให้ครบทั้งระบบได้ครับ เพียงแต่อยากคุยและล็อก scope ให้ชัดก่อน เพื่อเลือกวิธีทำที่เหมาะกับการใช้งานจริงและคุมค่าใช้จ่ายได้

## คำถามหลักที่ควรถามลูกค้า

1. **เว็บต้นทางที่อยากให้รองรับมีเว็บไหนบ้างครับ?**  
   ต้องการให้ระบบดึงได้ทุกเว็บเลย หรือเริ่มจากเว็บที่ใช้งานจริงและระบุมาเป็นรายเว็บก่อนครับ

2. **เนื้อหาที่จะนำมาแปลเป็นภาษาอะไรบ้าง และแปลไปภาษาไทยอย่างเดียวไหมครับ?**  
   มีตัวอย่างเนื้อหาจริงให้ลองประเมินคุณภาพคำแปลได้หรือเปล่าครับ

3. **คุณภาพคำแปลที่คาดหวังระดับไหนครับ?**  
   เน้นอ่านเข้าใจเร็ว ต้นทุนต่ำ หรือเน้นภาษานิยายลื่น ชื่อตัวละครและศัพท์เฉพาะคงที่เป็นหลักครับ

4. **หนึ่งตอนโดยเฉลี่ยยาวกี่คำหรือกี่ตัวอักษร และราคา 2–5 บาทหมายถึงต่อหนึ่งตอนจริงไหมครับ?**  
   ข้อมูลนี้ใช้คำนวณเครดิตและเลือก model tier ให้คุมต้นทุนได้

5. **เวลาแก้คำแปล อยากให้แก้เฉพาะจุดแล้วระบบจำคำศัพท์นั้นไปใช้ในตอนถัดไปด้วยไหมครับ?**  
   เช่น ชื่อตัวละคร ชื่อท่า ชื่อสถานที่ หรือสรรพนาม

## จุดเสี่ยงที่ควรคุยให้ชัด

### 1. การดึงเนื้อหาจาก URL

ไม่ใช่ทุกเว็บจะดึงได้เหมือนกัน บางเว็บใช้ JavaScript, มีระบบกัน bot, ต้อง login หรือมี paywall

**แนวทาง:** เริ่มจากเว็บที่ลูกค้าระบุ พร้อม preview ให้ตรวจเนื้อหาก่อนแปล และไม่รับปากว่า “รองรับทุกเว็บ” ตั้งแต่ v1

### 2. ลิขสิทธิ์ของเนื้อหา

ระบบช่วยแปลได้ แต่ต้องชัดว่าใครมีสิทธิ์นำเนื้อหามาใช้ จัดเก็บ หรือเผยแพร่

**แนวทาง:** กำหนดเงื่อนไขผู้ใช้, retention ของ source text และทางลบข้อมูลให้ชัด

### 3. คุณภาพคำแปลและการรักษาบริบท

นิยายมีชื่อตัวละคร สรรพนาม และศัพท์เฉพาะ ถ้าไม่มี glossary/context ที่ดี ชื่อและ tone อาจเปลี่ยนไปมา

**แนวทาง:** benchmark กับเนื้อหาจริงก่อนเลือก model และเก็บ glossary แยกตามหนังสือ

### 4. ค่า AI ไม่ได้มีแค่จำนวนคำ

context, glossary, retry และ Quick Fix ใช้ token เพิ่มทั้งหมด

**แนวทาง:** มีเครดิต, reserve usage ก่อนเริ่ม job, เพดานต่อ job และ usage ledger ที่ตรวจสอบได้

### 5. งานแปลตอนยาวใช้เวลา

ถ้าแปลทีละบทใน request หน้าเว็บโดยตรง ระบบอาจค้างหรือ timeout

**แนวทาง:** ใช้ background job/worker พร้อมสถานะงานและ retry ที่ผู้ใช้เห็นได้

### 6. เครดิตและ payment

webhook ซ้ำ, retry หรือ job ล้มเหลว อาจทำให้ตัดเครดิตซ้ำถ้าออกแบบไม่ดี

**แนวทาง:** ใช้ transaction ledger และ idempotency key ตั้งแต่ v1

### 7. Platform-managed API ต้องคุม usage เอง

ReadLead ใช้ provider key ของแพลตฟอร์มเท่านั้น จึงต้องรับผิดชอบ quota, provider error, rate limit และต้นทุนที่เกิดจาก user โดยตรง

**แนวทาง:** ใช้ credit reserve, usage ledger, per-job cap และ model tier Standard/Quality ตั้งแต่ v1

### 8. Scope บานได้ง่าย

“รองรับทุกเว็บ”, “แปลทุกภาษา”, “หลาย model tier”, “PromptPay” ถ้าต้องมีพร้อมกันจะเกิน MVP

**แนวทาง:** ล็อก source sites, ภาษา, model tier และ payment flow ก่อนเริ่ม

## ประโยคปิดเพื่อพาลูกค้าไปสู่การตัดสินใจ

> จุดที่อยากล็อกก่อนเริ่มคือเว็บต้นทางที่ต้องรองรับจริง คุณภาพคำแปลที่คาดหวัง และรูปแบบการคิดเครดิตครับ เพราะสามส่วนนี้มีผลกับทั้ง architecture, ระยะเวลา และต้นทุนของระบบโดยตรง
