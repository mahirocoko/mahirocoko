# ข้อเสนอขอบเขตงาน — ReadLead

**ReadLead** คือแพลตฟอร์มสำหรับอ่านและแปลเนื้อหาแบบต่อเนื่อง โดยเน้นประสบการณ์อ่านสบายตา การแปลที่รักษาบริบท และการแก้คำแปลเฉพาะจุดได้ทันที

เอกสารนี้ใช้ยืนยันขอบเขต MVP ก่อนเริ่มพัฒนา ราคาและกำหนดส่งจะสรุปหลังได้รับตัวอย่างเนื้อหา เว็บไซต์ต้นทาง และคำตอบในหัวข้อ “ข้อมูลที่ต้องยืนยัน”

---

## เป้าหมายของ MVP

1. ผู้ใช้ใส่ URL หรือวางข้อความเพื่อสร้างงานแปล
2. ระบบดึงเฉพาะชื่อเรื่อง/ชื่อตอนและเนื้อหาจริง ไม่ดึง navigation, ลิงก์แนะนำ, โฆษณา, comment หรือส่วนประกอบหน้าเว็บที่ไม่เกี่ยวข้องมาแปล
3. ผู้ใช้อ่านคำแปลใน Reader แบบเลื่อนต่อเนื่อง ปรับธีมและขนาดตัวอักษรได้
4. คำแปลรักษาชื่อตัวละคร สถานที่ และศัพท์เฉพาะผ่าน glossary
5. ผู้ใช้เลือกข้อความเพื่อแก้เฉพาะคำ ประโยค หรือย่อหน้าที่ต้องการได้
6. ระบบคิด usage เป็นเครดิตและแสดงประวัติการใช้ชัดเจน

---

## สิ่งที่จะส่งมอบ

### 1. Reader experience

- หน้าอ่านแบบ vertical scroll รองรับ desktop และ mobile
- ธีมอ่านสบายตา, dark mode, ปรับ font size และ typography ได้
- แสดง title และเนื้อหาที่ผ่านการคัดเฉพาะส่วนสำคัญแล้ว
- ปุ่มแปลตอนถัดไปสำหรับ source ที่รองรับ
- สถานะงานแปล เช่น กำลังเตรียมเนื้อหา, กำลังแปล, สำเร็จ หรือเกิดข้อผิดพลาด

### 2. Content import และการคัดเนื้อหา

- รับ URL และ paste text
- ดึงหน้าเว็บจากฝั่ง server พร้อมมาตรการป้องกัน URL ที่ไม่ปลอดภัย
- คัดเฉพาะ main content ก่อนส่งเข้า AI
- หน้า preview ให้ผู้ใช้ตรวจและตัดย่อหน้าที่ไม่ต้องการก่อนเริ่มแปล
- เก็บ URL ของตอนถัดไปเป็น metadata แยกจากเนื้อหาที่ใช้แปล

### 3. Context-aware translation

- แยกเนื้อหาเป็น segment เพื่อแปล แก้ไข และบันทึก revision ได้เป็นรายย่อหน้า
- ตั้งค่า genre/tone สำหรับรูปแบบนิยายที่ตกลงกัน
- Glossary ต่อหนังสือสำหรับชื่อตัวละคร สถานที่ กลุ่ม และศัพท์เฉพาะ
- ใช้ summary และ glossary ที่เกี่ยวข้องเพื่อรักษาความต่อเนื่องระหว่างตอน
- ตรวจ output ให้อยู่ในโครงสร้างที่ระบบนำกลับมาแสดงได้อย่างปลอดภัย

### 4. Highlight & Quick Fix

- highlight ข้อความคำแปลใน Reader
- เปิดหน้าต่างแก้เฉพาะส่วน พร้อมคำสั่งจากผู้ใช้
- ส่ง context เท่าที่จำเป็นไปยัง AI แล้วคืนเฉพาะข้อความ replacement
- แสดงผลแก้ไขและเก็บ revision
- เสนอเพิ่ม/แก้ glossary แบบผู้ใช้เห็นและยืนยันได้

### 5. Account, เครดิต และการชำระเงิน

- สมัคร/เข้าสู่ระบบด้วย Google OAuth และ/หรือ email-password ตามที่ตกลง
- ระบบเครดิตแบบ pay-as-you-go
- reserve เครดิตก่อนเริ่มงาน และตัดตาม usage จริงเมื่อจบงาน
- ประวัติการเติม/หัก/คืนเครดิตที่ตรวจสอบได้
- Stripe Checkout และ webhook สำหรับยืนยันการชำระเงินฝั่ง server

> การรองรับ PromptPay, สกุลเงิน และ payment method ต้องตรวจตามประเทศและสถานะบัญชี Stripe ของนิติบุคคลก่อนยืนยันใน scope

### 6. ระบบหลังบ้านขั้นต่ำ

- ข้อมูลผู้ใช้ หนังสือ ตอน คำแปล glossary และ credit ledger
- background job สำหรับการดึงเนื้อหาและแปลตอนยาว
- retry และสถานะ error ที่ผู้ใช้เข้าใจได้
- logging/monitoring ระดับใช้งานจริง

## แนวทาง model และการคิดเครดิต

MVP เสนอให้ใช้ **ReadLead-managed API**: ระบบถือ provider key ฝั่ง server แล้วขายเครดิตให้ผู้ใช้ ไม่ต้องให้ผู้ใช้ตั้งค่า API key เอง

เหตุผลคือ onboarding สั้น ควบคุมคุณภาพคำแปลได้ และคิดเครดิตได้ตรงไปตรงมา

ผู้ใช้จะเห็นตัวเลือกเชิงผลิตภัณฑ์ เช่น **Standard** และ **Quality** แทนชื่อโมเดลดิบ ส่วนระบบเลือก provider/model ตาม benchmark ของเนื้อหาจริง

เครดิตจะประเมินจาก:

```text
ต้นฉบับ + คำแปลที่คาดการณ์ + glossary/context ที่เกี่ยวข้อง + buffer สำหรับ retry
```

หลังงานเสร็จ ระบบตัด usage จริงและคืนส่วนต่างที่ไม่ได้ใช้ หากงานล้มเหลวจะไม่ตัดเครดิตซ้ำ

> BYOK หรือการให้ผู้ใช้ใส่ API key เอง สามารถเพิ่มใน phase ถัดไปได้ แต่ไม่แนะนำให้เป็นส่วนหนึ่งของ MVP เพราะเพิ่มงานด้าน security, support และความไม่สม่ำเสมอของคุณภาพ

## Milestone และเกณฑ์รับงาน

### Milestone 0 — Discovery และ quality benchmark

**สิ่งที่ทำ**
- รับ sample URL/ข้อความจริง
- เลือกเว็บต้นทางที่ต้องรองรับใน v1
- benchmark model, prompt, glossary และต้นทุนต่อ chapter
- สรุป acceptance criteria และ credit model

**เกณฑ์รับงาน**
- ตกลง sample content และสิทธิ์การใช้งาน
- มีตัวอย่างคำแปลที่ผ่านเกณฑ์ด้าน tone/ศัพท์เฉพาะ
- มีตัวเลขต้นทุนต่อหน่วยสำหรับตั้งราคาเครดิต

### Milestone 1 — Reader และ translation core

**สิ่งที่ทำ**
- Reader responsive
- paste text, segment translation, glossary และ translation jobs
- สถานะงานและประวัติการแปล

**เกณฑ์รับงาน**
- อ่านได้ดีบน desktop/mobile ตาม reference ที่ตกลง
- ชื่อ/ศัพท์ใน glossary ไม่แกว่งใน sample test
- งานแปลตอนยาวไม่ค้างหน้าเว็บและกลับมาอ่านต่อได้

### Milestone 2 — URL import และ Quick Fix

**สิ่งที่ทำ**
- URL extraction สำหรับเว็บไซต์ที่ระบุ
- content preview
- Highlight & Quick Fix พร้อม revision
- next-chapter flow สำหรับ source ที่รองรับ

**เกณฑ์รับงาน**
- translation input ไม่มี nav/link/ad/comment จาก sample URLs
- ผู้ใช้แก้เฉพาะ segment แล้วไม่กระทบย่อหน้าอื่น
- ระบบบันทึกคำแก้และ glossary ได้ตามสิทธิ์ของผู้ใช้

### Milestone 3 — เครดิตและการเปิดใช้งาน

**สิ่งที่ทำ**
- auth, managed credits, Stripe checkout/webhook
- usage ledger, error/retry, basic admin/support flow
- QA ด้าน security, cost guard และ launch readiness

**เกณฑ์รับงาน**
- เติมเครดิตและหักเครดิตจาก usage จริงได้
- retry/webhook ซ้ำไม่เกิด double charge
- ผู้ใช้เห็นยอดและประวัติที่ตรวจสอบได้

## สิ่งที่ไม่รวมใน MVP

- รับประกันว่าดึงเนื้อหาได้จากทุกเว็บไซต์บนอินเทอร์เน็ต
- bypass login, paywall, DRM หรือระบบป้องกันของเว็บต้นทาง
- native iOS/Android app
- BYOK หลาย provider ตั้งแต่วันแรก
- แปลทั้งเล่มแบบ batch โดยไม่มี sample benchmark/quality review
- EPUB/PDF export, collaboration หลายคน, public marketplace หรือระบบผู้แปลมืออาชีพ
- การตัดสินสิทธิ์ลิขสิทธิ์แทนเจ้าของเนื้อหา

---

## ข้อสมมติและความรับผิดชอบของลูกค้า

เพื่อให้เริ่มพัฒนาได้ตรง scope ลูกค้าต้องช่วยเตรียม:

1. Sample URL/ข้อความจริงอย่างน้อย 5–10 ตัวอย่าง พร้อมระบุเว็บไซต์ต้นทาง
2. หลักฐานหรือแนวทางสิทธิ์ในการนำเนื้อหามาแปล/จัดเก็บ
3. ตัวอย่างคำแปลที่ถือว่า “ดี” และรายการคำศัพท์/ชื่อตัวละครสำคัญ
4. Brand guide, logo และ reference UI เพิ่มเติมหากมี
5. ประเทศนิติบุคคล, สกุลเงินที่ขาย และ payment method ที่จำเป็น
6. ผู้รับผิดชอบตัดสิน acceptance ของคุณภาพคำแปลและคำศัพท์

---

## ข้อมูลที่ต้องยืนยันก่อนประเมินราคาและกำหนดส่ง

1. ผู้ใช้หลักเป็นผู้อ่านทั่วไป, ทีมแปล หรือทีม content
2. v1 แปลจากภาษาใดไปภาษาใดบ้าง
3. เว็บไซต์ต้นทางที่ต้องรองรับจริงมีอะไรบ้าง
4. นำเข้าแค่ title + body หรือรวมภาพ/เชิงอรรถ/author note
5. “แปลตอนถัดไป” ต้องทำงานอัตโนมัติระดับไหน
6. เกณฑ์คุณภาพคำแปลและวิธีอนุมัติ sample คืออะไร
7. Glossary เป็นของ user, book หรือ shared ทั้งระบบ
8. Quick Fix ต้องรองรับแค่ย่อหน้า หรือเลือกหลายย่อหน้าด้วย
9. ต้องมี free trial, เครดิตเริ่มต้น, subscription หรือ pay-as-you-go เท่านั้น
10. ต้องใช้ PromptPay จริงหรือไม่ และนิติบุคคลเปิด Stripe ในประเทศใด
11. ต้องเก็บ source text นานเท่าไร ผู้ใช้ลบข้อมูลเองได้ไหม
12. ปริมาณงานคาดการณ์: จำนวน user, chapter ต่อวัน และความยาวเฉลี่ยต่อ chapter

---

## สรุป

ReadLead ทำเป็นผลิตภัณฑ์ใช้งานจริงได้ โดยเริ่มจาก URL/text ที่ตรวจขอบเขตได้, managed credits, contextual glossary และ Quick Fix ระดับ segment ก่อน

เมื่อมีข้อมูลจากการใช้งานจริงแล้ว จึงค่อยขยายไปยังเว็บไซต์เพิ่ม, model/provider เพิ่ม หรือ BYOK โดยยังควบคุมคุณภาพและต้นทุนได้อยู่
