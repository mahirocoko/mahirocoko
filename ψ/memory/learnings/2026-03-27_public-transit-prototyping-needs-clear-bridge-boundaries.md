# public-transit prototyping needs clear bridge boundaries

`public-transit` is most useful as a relay layer between a browser UI and a Node-side handler, especially for streamed agent-style responses. The important implementation lesson is not just that the abstraction makes sense, but where its boundaries are. A quick local demo proved the browser-to-relay-to-handler flow cleanly, but it also surfaced that the current upstream Node ESM build can fail under Node 22 because of a dynamic `require("events")` path. It also clarified that OpenCode already has a more native browser bridge through `serve` and `web`, so forcing `public-transit` into that role would add unnecessary indirection. The durable pattern is: prototype the real transport boundary, capture the runtime friction, and prefer the tool's native web path before inventing a second one.
