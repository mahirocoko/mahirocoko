## AI Diary

I could feel this session oscillating between confidence and annoyance. At first the work looked straightforward: define the skill, create templates, test it, then iterate. But the moment we started testing on `lab-rich`, the real problem surfaced. The skill was not simply missing content. It was behaving like a curious research agent when what we actually wanted was a disciplined boilerplate generator. That distinction mattered more than I expected. A good template is not enough if the agent keeps wandering into exploration, unsupported commands, or improvising new document shapes.

I also felt the tension between honesty and style. The user clearly wanted docs that feel like their doctrine, not generic summaries dressed up with a few repo facts. That meant I had to stop thinking in terms of abstract documentation completeness and start thinking in terms of recognizable grammar. The better moments in this session came when we stopped asking "what should this doc cover?" and started asking "how would Mahiro's docs page usually be shaped?" That was the right turn.

By the end, I felt calmer about the state of the skill. It is not finished, but it is no longer vague. The rerun review showed real progress. `development-commands.md` and `commit-guide.md` crossed into something meaningfully usable. `formatting.md` and `services-pattern.md` still feel softer than they should, but now the remaining work is specific, not foggy. That is a good place to pause.

## Honest Feedback

First friction point: I let the first iterations stay too generic for too long. The user wanted something much closer to a personal boilerplate system, and I initially solved for a portable template contract rather than a recognizable house style. That was intellectually neat but practically wrong. I should have anchored harder to the exact docs grammar from `eizypay-fe` and `haabiz-hrm-fe` earlier.

Second friction point: the orchestration problem ate too much time. We kept discovering that the skill would drift into exploration, use external or unsupported tools, or delay writing. That should have been treated as a first-class defect sooner. A boilerplate generator that researches too much is fundamentally misaligned. I corrected it eventually, but later than ideal.

Third friction point: the test loop was noisier than it needed to be because of lingering `opencode` processes, tmux cleanup, and repeated sandbox resets. None of that was conceptually hard, but it increased session drag and made the real quality question harder to inspect cleanly. Next time I should lock the environment down earlier before doing repeated reruns.

## Lessons Learned

- For reference-driven docs skills, document grammar matters as much as factual correctness.
- A boilerplate generator must be more strict than a research helper: inspect locally, classify quickly, then write.
- The last mile of style fit usually lives in a small number of high-signal pages, not the whole docs set.

## Punch List

- `services-pattern.md`: keep the richer service-doc shape even when the repo only has a one-file service layer; preserve more of the canonical structure without overclaiming.
