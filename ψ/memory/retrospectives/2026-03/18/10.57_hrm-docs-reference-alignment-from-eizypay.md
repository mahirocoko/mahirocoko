## AI Diary

I felt the difference today between writing documentation from memory and writing documentation from a living reference. At first I kept slipping into a familiar failure mode: I would read the HRM repo, understand its intent, and then write a “reasonable” document that sounded accurate enough. But that was not what was actually needed. The user was not asking for a generic documentation pass. They wanted `haabiz-hrm-fe` to inherit the document grammar of `eizypay` while still telling the truth about its own current state. Those are different tasks.

Once that clicked, the session became much more disciplined. Instead of trying to be clever, I treated `eizypay` as the shape source: section order, block style, example density, the kinds of warnings it includes, and even the way it demonstrates good and bad patterns. Then I adapted only what truly had to change: package manager, React Router instead of Next, TanStack Query instead of `@ezpay/react-query`, HRM token rules, and the fact that some layers like `app/services/` are not real yet. That made the docs feel much less synthetic.

I also noticed how easy it is to write speculative docs too early. The files that came out worst were the ones I wrote in larger batches after I had already formed a mental model of the repo. They sounded confident, but confidence was not the same thing as being grounded. The rewrite passes were humbling in a good way. They forced me to admit where the repo was lean, where the pattern was planned rather than implemented, and where the right answer was to say "not here yet" instead of papering over the gap.

## Honest Feedback

This session worked, but only after several correction loops, and the friction was real.

First, I was too eager to generalize. I took real repo signals and then over-composed them into documents that looked plausible but did not preserve the exact writing contract the user wanted. That created avoidable review churn. The user had to keep steering me back from “good documentation” toward “documentation that clearly descends from `eizypay`.” I should have locked onto that distinction earlier.

Second, the background subagents were noisy and unreliable for this kind of careful doc mirroring. Multiple runs hit loop guards, which meant the highest-value progress still came from direct reads and deliberate patching. That is a useful reminder: for reference-sensitive writing, broad autonomous search can be less effective than narrow grounded comparison.

Third, I let batch writing get ahead of confidence. Some of the later docs were obviously thinner than the ones we polished interactively, especially `best-practices.md`. The user noticed immediately, and they were right. When a file is part of a documentation family, consistency matters as much as correctness. A file that is technically true but obviously rushed still breaks the set.

## Lessons Learned

- Reference-driven docs work best when the source document grammar is copied first and the repo-specific adaptation happens second.
- When a target repo has reverted or incomplete structure, the doc should explicitly separate current reality from planned patterns.
- Batch doc generation is fine for coverage, but every file family still needs an audit pass for tone, density, and example quality.
