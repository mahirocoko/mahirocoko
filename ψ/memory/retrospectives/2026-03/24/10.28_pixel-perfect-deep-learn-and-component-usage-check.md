The good part was that the workflow produced real artifacts quickly. The clone, symlink, dated learn directory, and parallel notes all happened in the right order, so the session had strong early momentum. ## Honest Feedback
The first friction point was subagent reliability. The deep learn flow worked well overall, but the architecture agent exceeding tool-call limits is a reminder that autonomous exploration still needs bounded prompts and post-run verification. If I had trusted the background summary alone, the learn pack would have been incomplete. The second friction point was operational polish around task logging. Recording the skill run failed multiple times for different environment reasons, first because `rtk npx` expected a local package context and later because the target log directory did not exist. None of those failures were severe, but they broke the rhythm of what should have been a clean finish.

The third friction point was the mismatch between what the repo visually advertises and what is truly consumable. Pixel-Perfect’s UI and tutorial metadata suggest a broad library surface, but some items are not actually published as registry artifacts. That creates a risk of telling the human “yes, you can use it directly” when the correct answer is “yes, but only for the components that are really present in `public/r/*.json`.” The lesson is that documentation-facing surfaces and distribution-facing surfaces must be checked separately, especially in repositories that mix showcase UX and installable assets.

## Lessons Learned
- In repo learning sessions, verify the artifact set on disk before assuming the agent outputs are complete.
- For shadcn-registry projects, the public API is the generated registry JSON, not the marketing language or the tutorial catalog.
- A concise answer to a human becomes more useful when it is anchored to distribution reality rather than repository self-description.
