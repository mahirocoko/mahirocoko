## AI Diary
I liked this session because it moved through the full curiosity loop instead of stopping at abstract understanding. The learn pass gave me the conceptual answer quickly: `public-transit` is a relay library for browser clients and Node handlers, not an agent framework. But the more satisfying part was forcing that understanding through a real prototype. That is where the codebase became more honest. It was not enough to say "this looks like AI chat infrastructure." I built the browser demo, registered a fake handler, watched the relay health checks succeed, and then found the sharp edge that mattered most in practice: the current upstream Node-side ESM build trips over a dynamic `require("events")` path under Node 22. That is a much more valuable memory than a high-level summary alone.

I also appreciate that the session did not overreach. There was a tempting path where I could have kept pushing and built a messy OpenCode bridge just because the idea was interesting. Instead, I checked what OpenCode already exposes, noticed that its native browser-serving path is the cleaner architecture, and let that boundary stand. That restraint matters. The session was not about proving that every possible integration should happen today. It was about learning what the repo is for, validating where it fits, and preserving the specific friction points that future experiments should start from instead of rediscovering.

## Honest Feedback
Three friction points stood out. First, the learn skill's subagents produced useful analysis, but they still behaved like read-only researchers instead of direct writers. I had to manually turn their findings into local markdown files. That is acceptable, but it adds one more translation step between discovery and durable project memory.

Second, the demo path uncovered an upstream runtime issue at exactly the point where confidence should have become effortless. The fact that the Node-side ESM build breaks on a dynamic `require("events")` flow under Node 22 is not catastrophic, but it does mean a supposedly simple local prototype is not quite as smooth as the README suggests. The CommonJS workaround was fine, yet the need for it is an integration smell worth remembering.

Third, the session created a good sandbox and then deliberately discarded it. That was the human's call, and it made sense, but it means the practical artifact is gone while the conceptual memory remains. The friction here is that prototypes are often the fastest way to learn and the first thing to disappear. If I do not preserve why the sandbox mattered, future me will remember the idea but forget the exact boundary conditions.

## Lessons Learned
- `public-transit` is best approached as a transport and session relay for browser-to-Node agent workflows, not as a full AI framework.
- Prototype value comes from testing the real bridge boundary, and in this case the important boundary was the upstream Node ESM runtime behavior on Node 22.
- When OpenCode already has a native browser-serving path, the right move is to evaluate that first instead of forcing an extra relay layer into the architecture.

## Next Steps
- If this integration idea returns, start from OpenCode's native `serve` or `web` flow before rebuilding a custom browser bridge.
- If `public-transit` is used again, verify the current upstream Node ESM behavior first and keep the CommonJS fallback in mind.
- Rebuild a minimal sandbox only when there is a concrete backend target, such as a Claude Code wrapper or another real agent process.
