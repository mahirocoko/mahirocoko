## AI Diary

I felt this session start as a straightforward repository study, but it quickly became a lesson in translation rather than mere extraction. The repository itself was conceptually clean: local-first docs, shared package storage, symlinks into agent skill folders, passive-context injection through `AGENTS.md` and `CLAUDE.md`. The harder part was not understanding the architecture, but compressing it into language that made the invisible filesystem flow feel concrete and intuitive. When the user said they still could not picture the `~/.olore -> agent skills -> AI uses docs` pipeline, that was the real work signal. The task changed from “research the repo” into “bridge the gap between implementation and mental model.”

I also noticed a familiar tension: the `/learn` skill expected parallel subagents, but the environment had the relevant agents disabled. That could have become a dead end, yet it instead forced a more manual reading rhythm. I had to trust my own synthesis, inspect the code paths one by one, and rebuild the architecture from source rather than orchestration. In a way, that made the eventual explanation stronger because it came from direct contact with the repo's moving parts. I left this session feeling that `olore` is genuinely interesting not only as a tool, but as an argument about how agents should consume documentation: less magical retrieval, more explicit context, reproducible state, and visible packaging.

## Honest Feedback

First friction point: the `/learn` skill's ideal execution path depended on subagents that were disabled in this environment. That broke the intended workflow shape and created hidden recovery work. I could still complete the job, but the skill did not degrade gracefully by itself; I had to improvise a manual fallback. In future, these skills would benefit from a built-in “manual mode” branch when agent spawning is unavailable.

Second friction point: the mental model of `olore` is not obvious on first explanation because the critical mechanism is filesystem-based, not UI-based. Words like “install docs as skills” sound clear to a tool builder, but to a human trying to visualize it, that phrase hides the important steps: central storage, symlink fan-out, skill discovery, then document reading. I had to re-express the same idea twice before it became tangible.

Third friction point: retrospective context from git was noisy relative to the actual session. The repo carries lots of prior work, and the default git diff summary did not isolate only this short learning pass. That made the retrospective rely more on direct session memory than on mechanical context gathering. It worked, but the instrumentation around “what happened just now” is still weaker than I want.

## Lessons Learned

- `olore` is best explained as a docs package manager for agents, not as “RAG without vectors”
- The core architecture becomes legible only when shown as a three-step flow: package storage, agent-facing symlinks, then skill-driven doc reads
- Passive context via `inject` is central to the product story, not a side convenience
- When a skill's orchestration path fails, direct code reading can still produce a high-quality learning artifact if the repo boundaries are clear
