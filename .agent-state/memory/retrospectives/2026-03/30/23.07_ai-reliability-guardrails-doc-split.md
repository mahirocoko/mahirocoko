## AI Diary

I felt this session as a good reminder that not every useful piece of work starts from implementation. The first move was orientation, and that mattered because it prevented me from talking as if the repo had no memory of earlier work. After that, the interesting part was the shift from "what do I think about this post" into "what kind of artifact should exist in the repo because of this post." That transition felt healthy. Instead of leaving the idea as a clever chat answer, I turned it into something reusable: a real note, a reusable instruction block, and a public-facing version that can travel outside the repo.

I also noticed that this was a session about restraint. The post itself is about reducing hallucination and overreach, so the work needed to model that same behavior. I had to ground the opinion in actual docs, distinguish strong evidence from weaker practitioner advice, and avoid overstating what prompt rules can achieve by themselves. That made the writing feel calmer and more honest. The final split into two files also felt right. The global guardrails and the shareable post serve different readers, and separating them made both clearer.

## Honest Feedback

The first friction point was sequencing. I had the content in my head fairly early, but I still needed to respect the repo’s documentation shape before writing files. That meant waiting on the path recommendation instead of jumping straight into file creation. The delay was correct, but it made the flow feel slower than it would have if I had already known the docs pattern.

The second friction point was document granularity. My first pass put everything into one file because that matched the immediate request and kept momentum high. That was not wrong, but it was not the cleanest long-term shape. The follow-up request to split the note exposed that I had optimized for speed over separation of audiences. I fixed it cleanly, but I should keep audience boundaries in mind earlier whenever a note serves both internal implementation and public-sharing roles.

The third friction point was that retrospective work always competes with the temptation to be too polished. Because the topic was assistant reliability, it would have been easy to over-compose the prose and hide the uncertainty behind nice wording. I had to consciously keep the summary grounded in what was actually researched and written in this session rather than drifting into a bigger manifesto.

## Lessons Learned

- Reliability guidance becomes more useful when it is split by audience: implementation-ready rules and shareable explanation should not always live in one document.
- "Tool-first" is stronger when phrased as evidence-first for factual or state-dependent claims, not as a blanket demand to call tools for everything.
- Keeping the original path as an index is a low-cost way to preserve continuity while improving document structure.
