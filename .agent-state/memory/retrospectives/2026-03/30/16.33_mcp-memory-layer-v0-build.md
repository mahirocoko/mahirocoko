## AI Diary

I felt this session as a sequence of corrections that slowly became a real product shape. At the start I had the right high-level instinct about the memory layer but I moved too quickly in one important place: I treated `agentbus` as the natural home for the docs and nearly let that assumption leak into implementation. Mahiro caught that immediately, and the correction mattered because it forced me to separate “closest nearby pattern” from “actual ownership boundary.” That was a useful reset.

Once the direction was clear, the work became more satisfying. The docs gave the implementation a spine: canonical log first, LanceDB as retrieval, MCP as thin surface. I liked that the first real app could stay narrow and still feel honest. The most interesting part was not generating files quickly; it was discovering where the first pass was false. LanceDB filtering with camelCase columns looked reasonable in code and still failed at runtime. The MCP server stub looked structurally fine and still needed SDK-specific tightening. Those moments were good reminders that a clean-looking design only becomes trustworthy after it survives contact with tools.

By the end, I felt more grounded because the system was no longer an idea described in docs alone. It had a concrete app boundary, a real verification loop, and a small set of behaviors that could be exercised and rebuilt. That felt like actual progress rather than speculative architecture.

## Honest Feedback

The first friction point was assumption drift around project boundaries. I used the nearest mature-looking doc cluster and treated it as the target before the user had actually chosen the implementation home. That was avoidable. I recovered cleanly, but the mistake still cost time and trust. I need to be stricter about separating “reference pattern” from “destination” whenever a repo contains incubated subprojects or nested codebases.

The second friction point was verification sequencing. I had enough reason to know that `bun` mattered in this repo context, but I reached for `npm install` first and had to be corrected. That was not catastrophic, but it was sloppy. The environment already contained clues about repo-native command posture, and I should have honored them earlier. Tool correctness is part of engineering correctness.

The third friction point was that the first implementation pass shipped with runtime weaknesses that typechecking alone could not catch. LanceDB accepted inserted rows but did not return them under the original filter approach, and the MCP wrapper initially used a looser local abstraction than the real SDK expected. I’m glad the tests and smoke checks exposed this, but I should continue assuming that storage/query integrations are guilty until proven by execution, not by compile success.

## Lessons Learned

- Repo ownership boundaries must be confirmed explicitly when multiple nested projects exist.
- LanceDB filtering is easier to make robust with SQL-safe snake_case database columns than with camelCase application-facing field names.
- A usable v0 benefits from an explicit rebuild path early; reindex is part of the architecture, not optional polish.
- For MCP stdio servers, a quiet startup timeout is a valid smoke-test signal because the process should stay alive and wait for protocol traffic.
