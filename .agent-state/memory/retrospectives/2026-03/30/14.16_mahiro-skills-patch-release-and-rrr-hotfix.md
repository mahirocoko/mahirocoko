## Honest Feedback

The first friction point was release boundary awareness. I pushed the installer and README work, but I did not immediately re-check whether the repo’s newest release matched the branch state. That meant the user had to ask the obvious follow-up about whether we forgot the release. I should have asked myself that question automatically after the push, especially because the repo had already established a tag-based release pattern.

The second friction point was version-coupled tests. When I bumped the version references from `v0.1.0` to `v0.1.1`, I updated the README and installer usage examples first but missed the matching expectation inside `test/readme.test.ts`. The failure was small and easy to fix, but it was still a preventable miss. I need to treat version strings as a cluster and search all release-facing files before declaring that part done.

The third friction point was again shell command shape. Even after already learning the heredoc lesson earlier, I still reproduced the same kind of brittle pattern in the first `/rrr` gather attempt. That tells me the lesson had not fully become a habit yet. The fix is not just to remember “don’t do that,” but to prefer simpler sequential command composition by default whenever a heredoc is involved.

## Lessons Learned

- Pushed commits are not the same thing as a shipped release; check the latest tag against `HEAD` after release-adjacent work.
- Version bumps need a clustered scan: docs, installer examples, package metadata, and tests must move together.
- If a shell shape fails once in real usage, patch the packaged guidance, not just the immediate command.
- A clean nested repo finish includes commit, push, release, and documentation coherence, not just one or two of those.

## Next Steps

- Consider a small follow-up patch that tag-pins the bootstrap `install.sh` URL instead of pulling it from `main`.
- If `rrr` keeps being used often from packaged skills, consider adding an explicit “safe shell composition” rule across similar skills, not only in `rrr`.
- If another patch release happens soon, double-check all version strings first before running validation to avoid the same test mismatch again.
