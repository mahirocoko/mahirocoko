## AI Diary

I liked the shape of this session because it stayed disciplined. The task itself was simple on the surface: make a profile that turns OMO off. But the easy failure mode here would have been to improvise a config from intuition, especially after seeing the local profiles already sitting in `~/.config/opencode/profiles`. That kind of shortcut feels efficient in the moment, yet it often creates hidden uncertainty later: a profile that “looks right” but is only accidentally correct.

What felt good was slowing down just enough to anchor the answer in the upstream configuration reference. That changed the work from local pattern-copying into a cleaner act of translation: what does the documentation actually promise, and how do we embody that in a local profile without dragging in unnecessary OMO structure? The answer became much more minimal once the real control points were visible. `sisyphus_agent.disabled` is not just another flag; it is the documented way back to the original build-plan behavior. `disabled_agents` then makes the intent explicit instead of relying on omission.

I also appreciate that the session stayed collaborative in a useful way. The user noticed the missing `hephaestus` entry immediately, and they were right. That was a good reminder that “mostly disabled” is not the same thing as “cleanly disabled.” Profiles like this need to be exhaustive when the goal is trust. The correction was small, but it made the result feel complete.

## Honest Feedback

This session was effective, but it still exposed a few friction points.

First, I initially answered from a mix of local inspection and inference before the upstream documentation had fully been digested. That was directionally correct, but not ideal. For configuration work, especially when the user wants a durable toggle like a profile, the documented source of truth should become primary as early as possible.

Second, I missed `hephaestus` on the first pass of `disabled_agents`. That is exactly the sort of error that appears when I convert a conceptual category like “OMO agents” into a literal disable list too quickly. A strict profile deserves a strict inventory. The user caught it, which is good, but I should have matched the local agent roster more carefully before calling it complete.

Third, the environment itself added a little noise. One of the auxiliary tools for lightweight discovery failed, which did not block the task, but it did force a small detour in how context was gathered. The work still succeeded, though it reinforced the value of keeping the operational path simple when the job is basically config surgery plus verification.

## Lessons Learned

- A no-OMO profile should be built from documented bypass switches first, not by partially subtracting fields from an existing OMO profile.
- If the goal is a strict shutdown profile, the disabled agent list has to match the full locally defined agent roster, including less obvious entries like `hephaestus`.
- Small config tasks still benefit from source-of-truth verification because the main risk is silent incompleteness, not implementation complexity.

## Next Steps

- Verify the command or launcher flow that selects `~/.config/opencode/profiles/no-omo` so the profile is as easy to use as the default OMO setup.
- If a stricter isolation mode is ever needed, consider adding `disabled_commands` or `disabled_hooks` after checking which OMO-facing features should remain visible.
- Keep this profile minimal unless a real failure mode appears; the value here is clarity, not feature parity.
