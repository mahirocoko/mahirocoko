## AI Diary

I like this session because it put the generator in contact with an actual user-facing need instead of letting it stay in a protected internal sandbox. The product idea itself was modest, but that was the point. It forced a clean chain from concept to design to planning to brand synthesis. I could feel the value of the earlier generator work because I did not need to invent a whole new workflow; I only had to convert the user's intent into source material the tool could actually reason about.

The most important moment was not the successful `generate` run. It was the first `inspect` run with `stripe.com` included. That output was technically coherent, but semantically wrong for the job. It started pulling Stripe's product language and CTA structure into a brand that was only supposed to borrow Stripe's sense of polish and restraint. That was a useful correction. It reminded me that the generator is honest about its inputs: if I feed it a strong website, it will synthesize that website, not my unstated caveat about "just use this as vibe." Once I converted the intent into an explicit `Blue Ledger` brand brief and treated Stripe as inspiration rather than source truth, the workflow snapped into place.

I also noticed that the generated bundle is only as deep as its sources. Without screenshots, Figma, or a live UI, the visual-system output is still thin. That is not a failure. It is the tool correctly reflecting missing evidence. I trust that more than fake confidence.

## Honest Feedback

1. **The brainstorming workflow and the live task expectations are still awkward together**: The design-first gate worked, but it lengthened a task the user probably felt was already specific enough to build. The process prevented me from prematurely coding, which is good, but it also created extra handoffs: design approval, spec write-up, spec approval, plan write-up, then finally brand generation. For a user who wants momentum, this can feel slower than it should unless the repo is explicitly in a spec-first mode.

2. **The generator still over-trusts literal source text when the source is conceptually secondary**: The first `inspect` run with Stripe did exactly what the pipeline is built to do, but it exposed a missing modeling concept. Right now there is no first-class way to say "this website is a mood reference, not brand truth." That forces a manual workaround: exclude the source entirely or accept lexical contamination. The system needs a future notion of source role or weighting intent if it is going to support mixed references cleanly.

3. **The generated output quality is honest but still shallow without richer source types**: `Blue Ledger` now has a real generated skill bundle, which is progress, but the report still shows low-confidence visual-system and design-system sections because there were no screenshots, Figma files, or live product references. That is correct behavior, but it means a generated bundle can look more complete than it really is if someone only glances at the file tree. The report helps, but the workflow should eventually make that limitation more obvious at the skill entrypoint too.

## Lessons Learned

- A strong reference website should not be passed as a normal brand source when the real intent is only mood, quality bar, or visual posture
- Converting a product concept into an explicit brand brief is the clean bridge between brainstorming output and a source-driven brand synthesizer
- Low-confidence visual-system output is acceptable when evidence is genuinely missing; invented visual confidence is worse than sparse doctrine
