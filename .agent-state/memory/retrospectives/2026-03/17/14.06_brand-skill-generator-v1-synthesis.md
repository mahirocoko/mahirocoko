## AI Diary

This was the kind of session I respect because it turned a fuzzy middle state into a clearer system boundary. At the start, `brand-skill-generator` was already beyond scaffold stage, but it still had too much "this technically works" energy. The output could be rendered, but too many parts were still evidence summaries wearing doctrine clothing. I spent most of the session tightening that gap. The important shift was mental, not just mechanical: I stopped thinking of the generator as "collect sources, rank snippets, print markdown" and treated it more like a synthesis pipeline with opinions about source trust, category boundaries, and surface context.

The best part was watching the rules become more legible as doctrine. `Voice anchor`, `CTA posture`, `Palette balance`, `Flow clarity`, `Visual restraint` — those are still heuristic, but they read like something a human could actually use. That matters. It means the system is beginning to emit guidance instead of just summarizing raw inputs.

I also noticed how easy it is to accidentally overfit to meta-docs when the only "brand docs" in the test case are implementation plans. That was a useful reminder: a good pipeline still needs real inputs to prove itself. The session ended in a better state than it began, but not because every hard problem is solved. It ended better because the next layer of problems is clearer now. The generator is usable. The unknowns are narrower. That is real progress.

## Honest Feedback

1. **The test data is still too synthetic**: We used `example.com`, internal spec docs, and local SVGs as stand-ins for a real brand. That was enough to prove architecture, but not enough to validate quality. The heuristics had to work around obviously non-brand inputs, which is partly why terms like `example` and doc-meta language kept leaking into synthesis. The system is ready for a real brand run, and delaying that test will just encourage more speculative tuning.

2. **The synthesis file is getting dense**: `build-normalized-brand-model-scaffold.ts` now carries a lot of the intelligence of the system. It is still coherent, but it is accumulating multiple responsibilities: source helpers, filtering heuristics, section-specific synthesis, profile composition, and conflict logic. This is manageable now, but if one more wave of sophistication lands there without extraction, the file will become harder to reason about and harder to tune safely.

3. **CLI help ergonomics are uneven**: The actual CLI help text is good now, but the package script path still produces Bun's help instead of the skill's help when invoked the wrong way. It is not a functional blocker, but it is sloppy UX for a tool that is trying to mature. Also, the docs update is still uncommitted at the time of writing this retro, which is correct for cleanliness but means the documentation work is not yet fully closed.

## Lessons Learned

- A brand synthesis pipeline becomes much more usable when section rules are synthesized as doctrine rather than copied from the top-ranked evidence
- Profile outputs need explicit context composition; simply reusing core rules is not enough for `marketing`, `product-ui`, and `dashboard`
- Source-driven tools should document their input model clearly, especially when users are likely to assume they accept freeform product prompts
