## Honest Feedback

1. **หลักฐานแน่นขึ้นตามลำดับ** — ตอนแรก Git history บอกได้เพียงชื่อ commit กับผู้เขียน แต่ยังยืนยันไม่ได้ว่ามีการกด `/init` จริง การใช้ recall ต่อจึงเป็นการขยายหลักฐานที่ถูกจังหวะ ไม่ใช่ค้นเพิ่มแบบไร้ทิศทาง
2. **คำแนะนำแรกยังหยาบไปนิด** — ผมบอกว่าควรเหลือ 16–18k ก่อนเห็นรูปแบบไฟล์ทั้งหมด พอ Mahiro ตกลงแล้วจึงย้าย project blocks ออกทั้งชุดและจบที่ 12,910 tokens คราวหน้าควรใช้ภาษาว่า “คาดว่าจะอยู่แถวนี้” หรือเสนอเกณฑ์เชิงพฤติกรรมก่อนตัวเลข
3. **การตอบเรื่อง `/recompile` ต้องอิง runtime จริง** — เอกสารยืนยันว่า conversation ใช้ long-term memory ร่วมกัน แต่ไม่ได้อธิบาย cache refresh ละเอียดพอ ผมจึงอ่าน implementation ของ Letta Code 0.30.14 และพบการเทียบ committed MemFS revision ต่อ conversation ตรงนี้ทำให้คำตอบแม่นกว่าการเดาจากข้อความ success ของ slash command

## Lessons Learned

- `/palace` เป็น inspection surface ส่วนที่มาของ memory ต้องตรวจที่ MemFS Git history
- Project-specific context ไม่ควรอยู่ใน `system/` เพียงเพราะเคยผ่าน `/init`
- การ demote memory ต้องย้ายเนื้อหา แก้ router และตรวจ cross-reference เป็นชุดเดียวกัน
- `projects-index.md` ควรเป็น always-loaded cue ที่บางพอ แต่ชี้ไปยัง overview/conventions ที่โหลดตามงานได้
- Token target เป็นแนวทาง ไม่ใช่เหตุผลให้เติม prompt จนกลับมาบวม
- บน local backend 0.30.14 conversation อื่นจะ refresh เมื่อพบ committed MemFS revision ใหม่ตอนกลับมาใช้งาน ไม่ต้องรัน `/recompile` ทุก conversation
