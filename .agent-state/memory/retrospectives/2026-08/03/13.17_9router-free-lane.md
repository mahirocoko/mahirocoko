## Honest Feedback

1. **benchmark รอบแรก confound หลายปัจจัยเกินไป:** prompt เดียววัด code, logic, Thai และ JSON พร้อมกัน ขณะที่ reasoning models ต้องใช้ output budget มาก ทำให้คะแนนแรกสะท้อน token configuration พอๆ กับ capability ผมควรแยก capability prompts หรืออย่างน้อยอ่าน usage/finish reason ก่อนประกาศ ranking
2. **ผมให้คำแนะนำ Mimo เร็วเกินหลักฐาน:** smoke test `OK` พิสูจน์ availability เท่านั้น ไม่ได้พิสูจน์ว่าเป็น default ที่ดีที่สุด หลัง benchmark จริง Gemma 4 31B และ MiniMax M3 เหมาะเป็น default มากกว่า การแนะนำโมเดลจากชื่อและ request เดียวควรถูกตีกรอบว่า provisional ตั้งแต่ต้น
3. **เอกสาร current state ต้องรับมือ human mutation:** docs แรกเขียน zero-credential เป็นข้อเท็จจริงปัจจุบัน ทั้งที่ Mahiro สามารถเพิ่ม connection ผ่าน dashboard ได้ตลอด เอกสาร operator ควรแยก invariant, install snapshot และ live check command ตั้งแต่แรก

อีก friction คือ Providers page แสดง Ollama `No connections` ขณะที่ API มี active connection จริง Source ชี้ว่าหน้า list fetch connections แค่ครั้งเดียวและมี status normalization ของตัวเอง ผมตอบด้วยหลักฐาน API และแนะนำ reload โดยไม่รีบแก้ upstream code แต่ควรจำว่าหน้าจอ, persisted state และ current request result เป็นคนละ evidence layer เสมอ

## Lessons Learned

- Catalog visibility ไม่เท่ากับ entitlement, free pricing หรือ route availability
- HTTP 200 ที่ไม่มี final content เป็น operational failure ไม่ใช่ success
- แยก quality failure ออกจาก timeout, 403 subscription gate, 404 route, 429 shared-pool limit และ reasoning-budget exhaustion
- Model tier ต้องมาจาก task-specific correctness + latency + reliability ผ่าน route ที่จะใช้จริง
- Current Reality ใน docs ต้องตรวจซ้ำหลัง human เปลี่ยน provider/credential state
- Free-only ที่มี API keys ไม่ใช่ zero-credential; boundary อยู่ที่ dedicated free-tier credentials และการไม่เขียน global config
- UI card อาจ stale แม้ database/API ถูกต้อง จึงต้องตรวจ source-of-truth API ก่อนสรุปว่าข้อมูลหาย
- Retry reasoning-heavy model ได้หนึ่งครั้งด้วย budget ที่เหมาะสม แล้วหยุดแทนการวน provider แบบไร้ขอบเขต
