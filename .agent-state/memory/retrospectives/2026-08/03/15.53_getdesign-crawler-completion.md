## Honest Feedback

1. **ตัวเลขครบทำให้มั่นใจเร็วเกินไป:** ตอนแรก 340 pages + 1,284 images ดูเหมือน complete แต่ 123 pages ยังซ่อน hero evidence อยู่ การตรวจ completeness ต้องรวม semantic utilization ไม่ใช่แค่ file-set equality
2. **Verifier รุ่นแรกใช้ regex กับ generated HTML กว้างเกินไป:** มันนับ `role="tab"` ที่อยู่ใน JavaScript selector ด้วย ทำให้ทั้ง 340 หน้า fail ปลอม การเปลี่ยนเป็น JSDOM คือ regression probe ที่ตรง defect shape กว่า และเตือนว่าการตรวจ markup ด้วย substring มีขอบเขตจำกัด
3. **Freshness contract มาช้ากว่า resume contract:** ผมทำ atomic checkpoint และ per-slug reuseก่อน แต่ยังไม่ bind detail กับ catalog-entry content ถ้า upstream เปลี่ยน slug เดิมระบบอาจ reuse metadata เก่าได้ Recheck รอบท้ายจึงยังพบ material bug ทั้งที่ full build ผ่านแล้ว

อีก friction คือ generated output เคยถูก commit มาบางส่วนทั้งที่ `.gitignore` มี `output/` อยู่ ทำให้สถานะ “ignored” กับ “untracked” ไม่เท่ากัน ต้อง `git rm --cached` และยืนยัน `git ls-files` เป็นศูนย์โดยเก็บไฟล์ local ไว้ การประกาศ output ownership ควรถูกวางตั้งแต่สร้าง lab แรกๆ

## Lessons Learned

- แยก catalog-index completeness, enrichment completeness, artifact completeness และ presentation completeness ออกจากกัน
- ถ้า primary collection field ว่าง ให้ตรวจ detail-derived fallback ก่อนสรุปว่าไม่มีข้อมูล
- Resume checkpoint ต้อง bind กับ source fingerprint ไม่ใช่ slug หรือ URL อย่างเดียว
- File existence ไม่พิสูจน์ download integrity; ใช้ temporary file, signature check และ atomic rename
- Generated HTML regressions ควรตรวจผ่าน DOM parser/browser ไม่ใช่ regex ที่นับ script strings ได้
- Multi-page viewer ควรใช้ semantic tabs; single-page branch ไม่ควรมี control ที่ไม่มีประโยชน์
- Corpus verifier ต้องตรวจ exact slug/file sets, stale extras, per-page rendering counts, links และ temp artifacts
- `.gitignore` ไม่ untrack ไฟล์ที่เคย commit แล้ว ต้องตรวจ `git ls-files` และใช้ cached removal โดยเก็บ local stateไว้
