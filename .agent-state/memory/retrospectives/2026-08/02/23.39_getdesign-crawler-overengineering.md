## Honest Feedback

Three friction points dominated. First, I failed ownership discipline. Once I learned that `lab/crawl-getdesign-md` was active concurrent work, the correct move was to leave it untouched and ask whether the catalog app was the intended target. Instead I edited it, then had to reconstruct it from captured output. Second, I overengineered before establishing the canonical source. Safety was not the problem; timing and layer ownership were. A two-request catalog extractor should have preceded image acquisition and importer hardening. Third, my verification cadence was reactive. Testing two or three items and handing off allowed heterogeneous records to fail one by one. The minimum acceptable proof should have been a complete first-page pass or a count comparison against the advertised catalog before presenting the script. The verifier caught real gaps, but adding more verifier loops did not compensate for choosing the wrong data source. I need fewer broad safety layers early, one stronger source-of-truth hypothesis, and earlier corpus-level validation.

## Lessons Learned

- For crawlers, locate the canonical data payload before designing per-item extraction or persistence.
- Use a count invariant early: if the UI advertises 328 and SSR yields 16, the first implementation is disproven.
- Prefer direct bundle/API/catalog extraction for discovery; detail pages should enrich records only when needed.
- A brace-balanced extractor is more resilient than regex tied to object field order when consuming minified object literals.
- Do not touch concurrent untracked work merely because it appears relevant. Confirm ownership and target path first.
- Safety controls are valuable only after the data-source and output contracts are correct.
- Validate a representative full slice before asking Mahiro to discover record-shape failures manually.
