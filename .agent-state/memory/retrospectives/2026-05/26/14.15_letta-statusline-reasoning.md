## Honest Feedback

Three friction points stood out. First, I should have remembered earlier that the new statusline API owns the whole idle row; the docs explicitly said not to preserve legacy left/right semantics, but the practical implication is that the custom renderer must recreate any desired right-side layout. Second, my quick direct mutation of local backend state was too optimistic. It was okay as an experiment because Mahiro asked for a quick “run function” style change, but I should have framed it as a risky live-state hack before implying it was done. Third, the `/project list` moment interrupted the reasoning investigation and I summarized a long list too aggressively with `...`; the skill contract wanted stable sections and complete tracked entries, while Mahiro’s actual focus was Letta Code. In future, when a slash command appears mid-investigation, I should complete the command cleanly but keep the active thread’s main question in mind and avoid losing the debugging throughline.

## Lessons Learned

- Letta Code 0.26.2 statusline extension renderers are full-row owners. If Mahiro wants built-in right-side information preserved, the custom extension must render agent/model/backend itself.
- Legacy `settings.json > statusLine.command` files can coexist with the new `~/.letta/extensions/statusline.tsx`; do not delete the legacy files unless Mahiro explicitly asks.
- `/reasoning-tab` is an opt-in Tab shortcut, not a reasoning panel. It only fires when idle, no autocomplete is active, and the current model has multiple recognized tiers.
- Statusline payload `reasoning_effort` reflects live runtime state, not necessarily what is present in local backend JSON after manual edits.
- For permission mode, the statusline field Mahiro means by “mode” is the Shift+Tab `permission_mode`, not the toolset.
- Color in terminal statuslines should encode state, not decoration: dirty/warning, clean/safe, accent identity, and high context pressure should be immediately scannable.
