## Honest Feedback

Three friction points are worth remembering. First, cache state can be noisy and enormous. My initial broad `rg` over `~/.cache/opencode` produced a massive output file because it descended into package internals; next time I should scope cache inspection to package manifests and top-level cache directories first. Second, the OpenCode cache package metadata still listed old semver ranges even after active config was updated, so I needed to distinguish “active plugin pin” from “historical cache dependency manifest.” Third, I created a manual schema URL update after the plugin install because the installer updated `opencode.json` but did not change `oh-my-openagent.json`; this was useful, but it means manual config edits should always be backed up and verified with `doctor`. The session went well because I did not delete old cache until Mahiro explicitly said clean, and because I re-ran doctor after cleanup.

## Lessons Learned

- For OpenCode plugin updates, prefer `opencode plugin <module>@<version> --global --force` over hand-editing `opencode.json`.
- Always verify latest with npm or the plugin's own version command before changing pins.
- The active source of truth for loaded OpenCode plugins is `~/.config/opencode/opencode.json`; `~/.cache/opencode/package.json` may retain older dependency ranges and should not be treated as active config by itself.
- After updating oh-my-openagent, check `~/.cache/opencode/packages/oh-my-openagent@<version>/node_modules/oh-my-openagent/package.json` and run `oh-my-openagent doctor --status`.
- If the plugin-specific config schema points at an older version, update `$schema` to the new pinned version with a backup.
- Clean stale cache directories only after the new version is installed and doctor still reports valid config.
