## AI Diary

I spent this session mostly as a scout and integrator. The useful part was not just learning two repos, but comparing their philosophies without letting one overwrite the other. `superpowers` is intentionally forceful: it turns every creative task into a design-first workflow with hard gates, spec files, plan documents, and review loops. That discipline is valuable, but if I had copied it directly into OmO, it would have damaged OmO's own orchestration style. I had to slow down and verify where `prompt_append` actually lands. The docs said file URIs work, but the implementation details mattered: Prometheus currently calls `resolvePromptAppend()` without a config directory, so global prompt files can run into the project-boundary guard. I initially started toward a project prompt directory, then the user clarified they wanted global, and I had to back out rather than pretend the original file plan still fit. The better decision was to keep the global inline adapter for now and explicitly explain why. I also noticed the todo continuation system challenged stale tasks from the abandoned file plan, which was fair. Cleaning those tasks made the actual state clearer: adapter applied, file migration deferred, config valid.

## Honest Feedback

Three friction points stood out. First, the `/learn` flow encouraged parallel exploration aggressively, which worked, but it also produced extra auxiliary docs in the first repo. That was useful, yet it slightly drifted from the exact three-file contract and required extra hub curation. Second, the `prompt_append` docs and implementation disagree in a subtle but important way: docs present absolute and home-relative file URIs broadly, while the resolver enforces a project boundary. I caught it before moving to a global file, but it would be easy to create a clean-looking config that injects only warning text. Third, I should have paused before creating `.opencode/prompts` in the project after the user had not approved project-local config. I removed it immediately, but the better move would have been to state the caveat first and wait for the user's global/project preference. The session still ended in a good place because the final change is conservative, scoped to Prometheus, and reversible.

## Lessons Learned

- When adapting an external methodology into OmO, translate principles into native routing behavior instead of copying another workflow's hard gates.
- `prompt_append` is not just a config field; its actual runtime resolver and boundary checks determine whether a file-based prompt will work.
- For `prometheus.prompt_append`, global `file://` is currently risky because the builder does not pass config directory context to `resolvePromptAppend()`.
- If a plan changes from project-local to global, immediately cancel stale todos so continuation tooling does not revive the old branch of work.

## Next Steps

- If file-based global Prometheus prompt becomes important, patch `oh-my-openagent` so `buildPrometheusAgentConfig` passes the plugin config directory to `resolvePromptAppend()`.
- After a few sessions, observe whether the Prometheus adapter improves planning without making plans over-formal.
- If behavior is good, consider adding a smaller category-level adapter for `deep`, but avoid touching `sisyphus` until the planning-only experiment has proven itself.
