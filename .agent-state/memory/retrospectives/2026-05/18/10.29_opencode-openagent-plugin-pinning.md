Three friction points: First, I started by checking the source clone and remote branch drift, which was a scope miss after Mahiro’s actual concern was runtime OpenCode plugin resolution. I should have prioritized `~/.config/opencode/opencode.json` first because the word “ผูกกับ opencode” was already in the original request. Second, I initially described `origin/dev` version `4.2.0` in a way that could imply “need to use 4.2.0,” even though npm/latest and tags were still `4.1.2`. The correct framing is released package versus unreleased dev metadata. Third, cache cleanup is inherently a little uncertain because OpenCode may maintain several cache roots and repopulate them on next run; I removed the obvious stale bare/latest paths, but I should avoid overclaiming “no cache” entirely. The robust fix is pinning the plugin spec so any cache is keyed to a precise version rather than `latest`.

## Lessons Learned

- For OpenCode plugin drift, inspect the runtime binding first: `~/.config/opencode/opencode.json`, `~/.cache/opencode/packages`, and npm published versions. Source/study clones are secondary unless the plugin uses `file://`.
- Avoid bare npm plugin specs like `oh-my-openagent` when cache correctness matters. Prefer exact version specs such as `oh-my-openagent@4.1.2`.
- Treat dev-branch `package.json` versions as unreleased until npm/tag confirms availability.
- When updating plugin configs, update both the plugin spec and related schema URL, and keep backups before changing global user config.

## Next Steps

- On next OpenCode launch, verify the resolved package in cache is `oh-my-openagent@4.1.2` if any behavior still looks stale.
- If OpenCode continues to prefer old cache roots, consider a small cleanup script for `~/.cache/opencode/packages/oh-my-openagent@latest` and bare `node_modules/oh-my-openagent` only.
- If a future `4.2.0` release appears on npm, upgrade by changing the exact plugin spec rather than returning to bare `latest`.
