## Key Findings

- The active local OMO config already had the important tmux/team switches enabled.
- `oh-my-openagent` tmux panes depend on both config and runtime environment: `TMUX`, `TMUX_PANE`, `tmux` on PATH, a running server/port, and successful `opencode attach` into spawned panes.
- Team-mode visualization is separate from ordinary background subagent tmux panes: it needs `team_mode.enabled` plus `team_mode.tmux_visualization`.
- The user’s current shell was inside `session=omo`, `window=0:node`, `pane_id=%0`, so the remaining diagnosis should focus on attach flow, layout mode, and upstream pane-spawn behavior rather than blaming the user’s tmux setup.
- `tmux.isolation: "window"` or `"session"` is a better next debug lever than continuing to question whether the user is inside tmux.

## Lessons Learned

- Do not stop at “run inside tmux”; verify `TMUX`, `TMUX_PANE`, and tmux’s own pane identity before assigning blame.
- For `oh-my-openagent`, tmux/team-mode pane failures can be config-correct but runtime-broken through server attach, layout capacity, or upstream race behavior.
- `tmux.isolation: "window"` is a good diagnostic step when `inline` panes fail or disappear.
- When a user already reports being in a specific tmux window/session, validate their claim quickly instead of repeating setup basics.

## Next Steps
