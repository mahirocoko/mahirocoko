## AI Diary

The useful turn in this session came when I stopped asking “which shiny effect should we copy?” and instead asked what contract made the source repository coherent. Libraries.dev contains five visually different packages and several rendering technologies, so copying one abstraction would have been the wrong lesson. The stronger idea was its Studio parameter specification: meaningful knobs, known bounds, presets, validation, and a live surface joined by one owner. PassCraft let me test whether that structure could compensate for my weaker visual taste without pretending that I had designed the look myself. Agy/Gemini supplied the visual/product recommendation, Mahiro chose the concept, and I stayed focused on contract integrity and evidence. That division worked, but only because I did not treat agent reports as proof. The first browser reviewer found genuine geometry and interaction failures, and the final reviewer still overstated sanitization while showing control characters in its own URL. Catching that mismatch reminded me that a confident “Ready” verdict is weaker than one contradictory byte of evidence. I also felt the cost of orchestration: callback recovery, a timed-out correction turn that was still working, and a lot of QA for a local mini-project. The result was robust, but future experiments should lock the reuse map and local-only ownership earlier so we spend effort where the hypothesis actually needs it.

## Honest Feedback

Three frictions stand out. First, I let a small mini-project grow into a fairly broad implementation before explicitly deciding whether it should be tracked or remain local-only. Mahiro ultimately chose local-only, and the cleanup was easy, but the catalogue row should never have been written before that ownership decision. Second, the Direct CLI control flow was noisier than the product work: one browser job briefly appeared finished while its background command resumed, and the correction prompt timed out even though Agy continued successfully. I recovered from the same receipt rather than rerunning, but callback-plus-report handling still consumed attention. Third, both the writer and reviewer made plausible overclaims. The writer initially duplicated parameter bounds despite the schema requirement, while the reviewer later called control characters sanitized even though its captured URL disproved that statement. Main inspection corrected both, but the better process is to build defect-specific disconfirming checks into the brief from the start. A fourth friction was proportionality: full visual QA was justified for the hypothesis, yet the implementation surface became larger than the simplest possible proof. A narrower first slice could have tested the same contract with fewer files.

## Lessons Learned

- When learning a visual repository, separate **contract reuse**, **runtime/package reuse**, and **visual inspiration** before implementation. PassCraft reused the first, selectively adapted the third, and intentionally skipped the second.
- One declarative schema is valuable even without a runtime AI agent: it can already own visible controls, limits, formatting, URL validation, and round-trip tests. Model tool-schema generation is a separate adoption step, not something to imply prematurely.
- Different visual jobs may deserve different rendering media. CSS gradients and 3D transforms, SVG geometry, and ordinary DOM controls were enough for this product; importing a WebGL renderer would not have made the hypothesis stronger.
- Visual-owner delegation does not remove Main's evidence duty. Inspect actual screenshots, geometry, URLs, and failure values; a reviewer can label a condition PASS while its own evidence contradicts it.
- Decide whether an experiment is tracked, incubated, or local-only before adding it to a current catalogue. An ignored app must not leave a tracked README entry that claims it is part of the active product surface.
