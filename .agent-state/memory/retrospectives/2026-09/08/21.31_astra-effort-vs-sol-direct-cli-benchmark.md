## AI Diary

The most important correction came from a short question: “ไม่ได้ใช้ direct cli หรอ”. I had built a defensible headless harness and was concentrating on hidden-test fairness, but that still missed the actual job. Mahiro was not asking for an abstract API benchmark; he wanted evidence about the interactive Direct CLI workflow we use. I am glad the question arrived before any model calls, because changing the execution owner afterward would have invalidated the comparison or forced wasteful reruns. Once the panes were visible, the benchmark became more informative than a clean base-model contest. Sol High followed the globally installed brainstorming workflow so strictly that it requested confirmation twice despite a direct implementation prompt, while every Astra effort implemented immediately under the same environment. That is a workflow result, not proof that Sol cannot code, and keeping that distinction explicit matters. I also had to confront defects in my own evaluator. Three shared failures were caused by assumptions or ambiguous wording in hidden checks, not candidate quality. Correcting those tests uniformly and regrading without reruns was the honest move, even though it changed the headline numbers. The session reinforced that benchmark machinery deserves the same skepticism as model output. A clean score is not trustworthy until task contract, harness, grader, and execution reality agree.

## Honest Feedback

Three frictions should change future runs. First, I initially optimized for reproducibility by building a headless `codex exec` runner even though our established Direct CLI definition is pane-first and visible. The harness was technically reasonable but operationally wrong for Mahiro's question; I should have named the execution contract before implementing it. Second, the first Easy timing wrapper used zsh's read-only `status` variable. Model work completed, but the wrapper exited unsuccessfully afterward, forcing me to recover elapsed values from task durations. This did not require reruns, yet it was avoidable with one shell smoke test. Third, hidden-test design was not fully locked before execution. The fairness verifier caught major structural issues before calls, but three semantic assumptions surfaced only after all candidates failed identically. I corrected them without favoring a model, but a predeclared contract table mapping each assertion to exact prompt wording would have reduced evaluator churn. A fourth limitation is dispatch control: the main tool scheduler staggered shell starts by roughly 30 seconds despite one parallel request. Individual timings remain useful, but future latency comparisons should use one receipt-bound fanout process with randomized arm order or serial randomized trials.

## Lessons Learned

- Establish whether the benchmark target is **base-model capability** or the **real configured workflow** before building the runner. This session validly measured the latter.
- A Direct CLI model/effort comparison needs visible startup evidence, fresh sessions, exact task ownership, and no arm-specific follow-up.
- Shared candidate failures are a signal to audit the evaluator before interpreting them as model weaknesses.
- Report correctness, elapsed time, and context/cost proxies separately. A model that exits early at a confirmation gate is not “fast” at implementation.
- One trial per task is routing evidence, not a universal ranking. Keep conclusions bounded to the task family, current plugins/rules, and observed runtime.
