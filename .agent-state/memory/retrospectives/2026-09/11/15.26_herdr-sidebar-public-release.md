# Session Retrospective

## Session Summary

We turned a temporary Herdr sidebar preview into a permanent stateless plugin, integrated its cache lifecycle with Mahiro Mods, corrected two live-only liveness failures, and released both sides. The plugin then passed a separate public-readiness audit, was hardened as an MIT open adapter, and became public as v0.2.0. Before this retrospective, the local pulse retained 220 sessions, no session yet recorded for September 11, and a +50% seven-day session change; the refreshed pulse includes this session.

## Timeline

- Reconstructed the accepted sidebar anatomy and separated presentation ownership from Mahiro Mods' cache/model lifecycle ownership.
- Built the dependency-free `mahiro-herdr-sidebar` plugin around bounded one-shot Herdr actions and targeted pane events, with exact sequence/TTL semantics and reversible configuration snapshots.
- Connected Letta model, reasoning, context, provider, Codex, Gemini, and Claude-GPT metadata without pane-content, transcript, credential, raw-provider, network, watcher, or daemon access.
- Ran isolated tests, live Herdr event/action probes, exact sequence and TTL experiments, configuration recovery tests, and a human visual gate.
- Released the initial plugin commit and Mahiro Mods v0.9.3, then caught a real liveness gap: refreshed caches did not republish short-TTL rows during idle panes or long turns.
- Added bounded cache-write-triggered refresh in Mods and corrected partial same-model events that temporarily omitted provider evidence; released Mods v0.9.4 after steady-state live proof.
- Audited the plugin for public exposure. Secret scanning found no leaks, but public adoption was initially blocked by missing licensing, private wording, incomplete producer onboarding, and lifecycle failure paths.
- Mahiro selected MIT plus an open-adapter boundary rather than bundling collectors. We documented the normalized cache/token protocol, added configurable cache ownership and macOS/Ubuntu CI, and retained `private: true` only as npm-publish protection.
- Independent verification found post-mutation command counterexamples. We changed link/enable/disable/unlink workflows to inspect exact owner-bound postconditions and restore captured config, snapshot, mode, and enabled state only when recovery remained safe.

## AI Diary

This session was a strong example of why I should distrust polished snapshots and ask whether the system stays true after time passes. The first sidebar looked correct, the tests were green, Mahiro accepted the visual result, and both repositories were released. Only the final liveness check showed that the quota cache could be fresh while Herdr metadata had already expired. I was tempted to treat focus/activity events as sufficient, but the observed idle pane disproved that architecture. The bounded cache-write notification was better because it reused an existing owner timer rather than adding a daemon. A second live failure taught the same lesson at another boundary: Letta sometimes supplied the same model with provider omitted, and our “missing means withdrawn” assumption erased correct Codex attribution. Public-readiness review was similarly valuable. The source was safe to expose, but safety was not the same as being useful or responsibly reusable. I also made avoidable coordination errors: one commit delegation had a mistyped model ID, and a CI monitor used zsh's read-only `status` variable, producing a false failure alert even though CI passed. Both were recoverable, but they created noise late in a long release. The best part was refusing to hide those misses. We checked actual GitHub jobs, fixed the monitor lesson in memory, and only claimed public readiness after post-mutation failure cases and unauthenticated access were proven.

## Honest Feedback

First, the initial architecture review overtrusted event activity and did not model the quiet-state case early enough. A short TTL plus cache refresh plus event-only projection should have produced an explicit liveness matrix before release, not after it. Second, the private-to-public audit became more expensive than necessary because broad agents generated very large reports for a repository with only a handful of files. The findings were useful, but Main could have framed tighter questions around licensing, producer availability, and transaction failure postconditions. Third, I accepted command exit status as a stronger signal than it deserved in install/uninstall workflows. A local CLI can mutate registry state and then return an error; recovery must inspect exact ownership and postconditions before deciding whether to roll back. Fourth, I introduced two avoidable orchestration mistakes near closeout: the `ggpt-...` model typo and zsh `status` assignment. Those did not damage code or GitHub state, but they interrupted trust and momentum. Finally, we released v0.9.3 before the idle-TTL proof. The follow-up v0.9.4 was correct and transparent, yet a better pre-release liveness check would have avoided the rapid patch release.

## Lessons Learned

- A visually accepted and test-green integration still needs a quiet-state liveness probe when caches, TTLs, and event-driven projection have different clocks.
- Missing fields in partial host event contexts are not automatically semantic withdrawal; preserve complete evidence while the identity key is unchanged and replace it on explicit identity/provider changes.
- Public source exposure, open-source licensing, and public adoption readiness are distinct gates.
- External mutating CLI commands require owner-bound postcondition inspection because failure may occur before or after mutation.
- Recovery should restore exact captured state only while registry/config ownership remains unambiguous; fail closed after owner replacement.
- Package `private: true` can safely prevent accidental npm publication in an otherwise public GitHub repository when distribution uses another channel.
- In zsh-backed monitor scripts, avoid assigning the special read-only parameter `status`.
