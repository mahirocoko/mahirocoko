## AI Diary

I entered this task with a technically correct but incomplete intuition: Apple's fluid-interface guidance is strongly motion-centered, so a motion lab seemed like the most honest first proof. That choice worked mechanically, but I did not surface its interpretive consequence early enough. Because the resulting artifact was almost entirely about direct manipulation, momentum, springs, interruption, and rubber-banding, Mahiro reasonably had to ask whether the skill was animation-only and then whether it was actually a taste-design skill. I should have framed that boundary before implementation: the skill teaches interaction behavior first, while its material, typography, accessibility, and broader design-foundation sections do not amount to a whole-page visual taste owner.

The implementation loop also reminded me why writer self-checks cannot close frontend work. The first Agy report was confident and green, yet Main audit still found mobile clipping, broken accessibility contracts, stale refs, and over-broad keyboard capture. The correction writer improved those, but still left a wrong provenance commit and a bubbled Space-key conflict. Fresh QA then found a missing focus ring that source checks and screenshots had not exposed. Finally, Chrome DevTools MCP could not prove the core pointer contract, so using a narrow Playwright fallback was justified rather than redundant. I am satisfied with the final evidence, but the path was more serial than ideal. The strongest part was refusing to convert partial checks into a whole-product PASS.

## Honest Feedback

Three friction points mattered. First, the initial implementation lane overclaimed accessibility and responsive readiness from a desktop self-check. A better dispatch would have made the 390×844 viewport, OS reduced-motion behavior, and focused-control keyboard isolation explicit from the beginning. Second, direct-cli callback guards twice treated temporary lifecycle states as possible completion before the agent had written its terminal report. Recovery correctly deferred when work was still active, but the extra waiting and capture steps added noise; persisted report sentinels remained the reliable owner. Third, the QA sequence was mechanically correct but lengthy: Chrome DevTools was the right first choice for layout and focus, while Playwright became necessary only for real pointer input. That fallback was evidence-driven, yet future labs should identify the one behavior that requires low-level input earlier so the test plan can reserve one compact specialized pass instead of discovering the gap late. No user data or unrelated server was disturbed; an existing port-5173 frontend-taste-lab server was correctly preserved.

## Lessons Learned

- Frame `apple-design` as Apple-style interaction/motion doctrine with supporting material, typography, accessibility, and foundational guidance—not as a visual-taste owner.
- Pin third-party project-local skills with upstream repository, exact commit, license, and content hash; do not let a generated report substitute an unrelated local worktree commit.
- Writer checks establish implementation sanity, not acceptance. Fresh browser QA remains necessary for focus paint, responsive containment, control isolation, and console health.
- Match evidence tools to the actual contract: Chrome DevTools MCP for rendered layout/computed paint, Playwright only when real low-level pointer sequences are materially required.
- Keep human visual/product acceptance separate from agent-owned technical readiness.
