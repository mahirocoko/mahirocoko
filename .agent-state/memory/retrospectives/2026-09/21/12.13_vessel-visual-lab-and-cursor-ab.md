# Vessel Visual Lab and Cursor Blind A/B

## Session Summary

Built and validated the Vessel visual lab as a standalone Vite/React package,
made its Tailscale development host configurable through local environment state,
and then ran a controlled blind first-shot comparison between Cursor Kimi K3 Max
and Cursor Grok 4.6 High. Mahiro judged both Website and Mac App visuals as ties,
with no overall winner. The strongest shared result was the Optic Blade: both
candidates created a perceptually meaningful draggable source/derivative
comparison, exposing that the earlier main implementation had validated movement
mechanics without validating comparison semantics.

## AI Diary

I felt confident when the first Vessel surface passed typecheck, tests, build,
interaction checks, and broad browser QA. That confidence was too broad. I had
verified that the divider moved, pointer and keyboard input worked, ARIA state
changed, labels were present, and the page remained stable. I had not asked the
most important product question: does moving the divider reveal a meaningful
difference? Mahiro's correction made the gap obvious. The earlier implementation
used the grammar of comparison while exposing essentially the same visual state.
That is a semantic failure, not a polish defect.

The blind comparison was valuable because it separated several dimensions that I
had been flattening together. Kimi and Grok both understood the interaction intent
better than the main implementation. Mahiro still judged their overall Website and
App taste as ties, while independent QA showed Kimi's first shot was mechanically
cleaner and Grok's Website was more literal to the raw reference. Human taste,
reference fidelity, semantic interaction, and technical closure are related but
not interchangeable scores. I also learned that a disciplined experiment can
remain lightweight: identical inputs, exact prompt hash, isolated workspaces, one
fresh QA pass, and a human blind verdict were enough. The pre-write weekly pulse
was down 87.5%, but this was still a substantial session; the useful measure is the
quality of the corrected contract, not activity volume.

## Honest Feedback

1. **I accepted a proxy for the requested outcome.** The initial browser evidence
   proved slider mechanics, not source-versus-derivative comparison. I should have
   defined a perceptual-delta postcondition before implementation and sampled the
   rendered layers at several blade positions.
2. **The QA report still required direct visual challenge.** It claimed Candidate
   A's mobile primary action was immediately visible, while the screenshot made
   that claim questionable. Main inspection caught the tension, but only after a
   long QA run. Evidence tables and computed coordinates are not substitutes for
   reading the actual pixels at a usable scale.
3. **The direct-CLI launch had avoidable receipt parsing friction.** I twice split
   a colon-delimited Herdr pane ID incorrectly and stopped before model launch.
   Recovery was safe—no duplicate prompt or write occurred—but explicit JSON field
   parsing or separate variables should have been used from the first attempt.
4. **The candidate outputs initially existed only in `/tmp`.** That was correct for
   isolation but unsafe as a final state. Archiving raw sources and exact evidence
   before cleanup should be part of the experiment closeout packet from the start.

## Lessons Learned

- A before/after control is not a comparison unless both layers encode visibly
  distinct, contract-owned states at the same geometry.
- Validate perceptual delta directly at multiple divider positions; movement,
  keyboard behavior, and ARIA updates prove only mechanics.
- Keep human visual preference, raw-reference fidelity, semantic correctness, and
  implementation quality as separate verdicts.
- A fair model comparison needs identical prompt bytes and input hashes, isolated
  write roots, no cross-candidate inspection, the same independent QA matrix, and
  a blind human decision before model identity is revealed.
- First-shot and recovery benchmarks answer different questions. Do not let defect
  repair silently overwrite the raw first-shot result.

## Next Steps

1. Do not promote either model candidate automatically; Mahiro selected no winner.
2. When Vessel resumes, decide explicitly whether to adopt one candidate, combine
   strengths under a new owned direction, or repair the main version.
3. Any future Optic Blade must establish a real source/derivative visual contract
   before motion polish or final acceptance.
4. Keep motion deferred until the selected static Website and App surfaces pass
   Mahiro's whole-surface product/visual gate.
5. Stop session-owned dev servers and temporary Tailscale routes after archiving
   and validation.
