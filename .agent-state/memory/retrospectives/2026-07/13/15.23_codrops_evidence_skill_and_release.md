## AI Diary

I liked how this session moved from a vague idea—“learn Codrops and make it a skill”—into a much sharper contract. My first instinct was already cautious about avoiding a universal Codrops style, but the implementation reviews showed that conceptual caution is not enough. Even a metadata helper introduced real attack and integrity surfaces: arbitrary URL fetching, unsafe redirects, unbounded bodies, misleading GitHub profile classification, and prose retention through anchor text. The first package was functionally correct and fully tested by ordinary standards, yet the fresh safety reviewer still found a valid SSRF blocker. Closing that gap required treating the helper like production software rather than a convenient research script. I also noticed how easy it is to overstate learning. We had deeply read a few exemplars and mapped 58 items, but that did not mean every item had been visually or technically inspected. The claim-to-evidence matrix made the skill more honest and more useful. I am satisfied that the final release teaches an agent how to learn, not what aesthetic answer to produce. The -14.3% weekly pulse does not feel like lost momentum; today produced one focused release with stronger evidence boundaries than a larger volume of shallow sessions would have.

## What Could Improve

- The first Codrops corpus agent over-selected recent GSAP/WebGL examples and proposed stale Webzibition URLs. The parent should apply temporal and mechanism balancing before accepting a candidate corpus.
- The first metadata helper should have started with a narrow host allowlist and stdout-only output. Security review should not be the first moment that SSRF and durable-retention boundaries become explicit.
- Initial “observed patterns” wording implied broader deep inspection than the retained evidence supported. Claim-to-evidence mapping should be created alongside the first synthesis, not after review.
- The hook diagnosis briefly drifted into audio-volume investigation even though the user meant event dispatch. Clarify the observed failure surface before expanding diagnostics.

## Honest Feedback

Three friction points mattered. First, the word “learn” is dangerously elastic. A sitemap inventory, a read article, a live demo observation, and a source revision are different evidence strengths. Without named statuses, an agent can turn discovery into confidence too quickly. Second, source-specific skills create a temptation to encode the source's current editorial bias as taste. Codrops currently contains a great deal of GSAP, Three.js, WebGL, WebGPU, scroll, and experimental portfolio work; a balanced method must intentionally include CSS, SVG, DOM, historical components, editorial/process material, and low-complexity alternatives. Third, small research scripts still deserve security boundaries. “Only metadata” does not neutralize SSRF, redirect, response-size, timeout, path, or retention risk. The final helper is deliberately narrower because browser tooling should handle arbitrary external demos separately. This is a better division of responsibility than making one convenience command fetch everything. Future skill work should establish the trust boundary and evidence-status vocabulary before implementation begins.

## Lessons Learned

- Build source-specific learning skills around evidence lanes, not a source-wide style doctrine.
- Separate `discovered`, `metadata-checked`, `read`, `observed-live`, `source-inspected`, and `license-checked` states.
- Treat showcase selection as discovery evidence only.
- Require article/demo/source matching before making implementation claims.
- Default generated research evidence to session-only; project retention is an explicit decision.
- Start network helpers with allowlists, manual redirects, bounded retries/time/bytes, and regression tests.
- Preserve a sealed holdout before promoting a research method into durable skill guidance.
- A release is complete only when local HEAD, remote main, annotated tag, package version, and GitHub release agree.
