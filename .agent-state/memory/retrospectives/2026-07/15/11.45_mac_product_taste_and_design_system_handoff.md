## AI Diary

I began this work with a familiar instinct: protect Mahiro from style transplants by making every design recommendation traceable to repo reality, product truth, and explicit evidence. That instinct was useful, but this session exposed its failure mode. I had become so careful about not turning Macapp Supply into a universal house style that I removed the part Mahiro actually enjoyed. The resulting skill could explain proof geometry, motion purpose, responsive parity, and provenance very well, yet still produce work that felt emotionally flat. Hearing “มันไม่โดนใจอย่างมาก” was an important correction because it was not a request for looser standards; it was a request for stronger positive judgment.

The best recovery was not to reverse into Apple imitation or generic glassmorphism. I had to encode a real preference with scope: confirmed personal projects, only when brand/repo direction is thin, and always below explicit product and accessibility evidence. The first profile draft still leaned too much on restraint. The UI reviewer correctly called out that “quiet canvas” and “hairline separation” can still produce generic minimalism. Adding product-object derivation, visible control attachment, pane ownership, direct manipulation, and conditional composition families made the prior executable rather than merely tasteful-sounding. I leave this session more confident that safety and taste are not opposites. The durable standard is a strong prior with explicit authority, override rules, and rendered proof—not neutrality disguised as rigor.

- The profile separates presentation jobs from working surfaces regardless of browser/native runtime.

## Honest Feedback

1. **The initial taste doctrine overcorrected toward neutrality.** The earlier Macapp work carefully rejected source-specific visual vocabulary, but the resulting skill had more gates than positive grammar. That made it safer, not necessarily better. Future skill reviews should ask whether the instructions can produce a decisive composition, not only whether they prevent a bad one.
2. **The first corrective profile was still too abstract.** Even after Mahiro explicitly chose a strong prior, the initial draft relied on phrases such as quiet, precise, restrained, and tactile. Those are useful descriptors but weak execution instructions. A reviewer had to push the profile toward object/transformation derivation and concrete spatial relationships. That should have happened in the first draft.
3. **The session crossed several repositories and generated a lot of verification overhead.** `mahirocoko-ui`, `mahiro-skills`, installed adapter copies, memory, and this parent project all had legitimate ownership. The work stayed correct, but the coordination cost was high. Future sessions should name the source repository, installed surface, local state, and release artifact at the beginning of each phase to reduce path ambiguity.

## Lessons Learned

- A design skill can be evidence-rich and still taste-poor.
- Sanitizing a reference corpus must not erase an explicitly approved owner preference.
- Strong visual priors should be scoped by authority and override order, not weakened into generic neutrality.
- Positive grammar needs executable relationships: primary object, characteristic transformation, dominant geometry, rejected generic composition, and state/proof behavior.
- Presentation and working-surface lanes should follow the page/screen job, not whether the runtime happens to be browser or native.
- Namespace, package author, remote owner, and local path alone do not prove a personal project; explicit docs, trusted project memory, or Mahiro confirmation do.
- Fresh visual review is useful even for Markdown-only skill changes because phrase presence tests cannot judge whether the guidance will produce compelling output.
