## AI Diary

I was strongest when I treated generated assets and rendered UI as evidence rather than as outputs to defend. Rejecting the first combined hero, preserving the source-lane report, and composing the accepted product renders was the right product-quality move. I was weaker in how I framed review results. I let a narrow reviewer prompt produce a “PASS,” then repeated that word as if it applied to the whole website. Mahiro immediately noticed the mismatch. The problem was not merely wording: my prompt had scoped the reviewer too narrowly, so the evidence could never justify a whole-product claim. The same pattern appeared in typography. I changed the hero and PDP but left `Arial Narrow` embedded in the broader display token; visually, that meant the system was still split even though the headline screenshot looked improved. Mahiro's correction forced me to inspect token ownership rather than isolated selectors. Once I renamed the token to `--logo`, searched every usage, recalibrated every affected size, and verified computed fonts, the design finally became one system. The four-day rrr-derived streak is encouraging, but this session is a reminder that momentum is only valuable when the acceptance claim matches the scope of the evidence.

## What Went Well

- Preserved the first proof instead of destructively rewriting it.
- Created an original brand/product thesis rather than repainting a generic storefront.
- Used asset contracts, provenance, visual inspection, and promotion gates.
- Refused to promote a combined hero that failed product-family and mobile-crop checks.
- Built meaningful commerce/app interactions rather than only visual sections.
- Recovered from direct user corrections without defending the previous result.
- Re-ran real browser checks at desktop/mobile after structural and typographic changes.
- Final source search proved condensed typography is logo-only.

## What Could Improve

1. Define the acceptance scope before asking a reviewer for PASS/FAIL.
2. Audit design-token ownership before changing individual components.
3. Start whole-page reviews from full-page screenshots earlier, not only viewport sections.
4. Treat commerce anatomy and buying confidence as part of the initial brief, not a late correction.
5. Avoid repeated overline + giant-heading + paragraph + grid formulas even when each section looks polished alone.

## Honest Feedback

There were three main friction points. First, I over-trusted targeted UI-review results and used “PASS” without preserving the qualifier. A typography regression pass cannot certify brand composition, commerce completeness, or mobile pacing. Second, I optimized locally before auditing globally. The hero and PDP moved to a non-condensed stack, but the old display token still controlled section headings, products, prices, builder values, journal, search, and cart. That was a systems failure, not a missed selector. Third, the first implementation still reflected the shape of a design exercise: attractive editorial sections, a clever hero collage, and a configurator, but insufficient buying-path clarity. The corrective Starter 01 offer, finish honesty, product-led materials proof, quieter journal, and earlier PDP action should have been part of the first complete-commerce definition. The session ultimately landed well, but Mahiro had to challenge claims twice before the review scope and typography ownership became rigorous.

## Lessons Learned

- A pass label must include its scope: typography pass, interaction pass, or whole-product pass.
- Whole-product acceptance requires full-page desktop/mobile composition plus exercised commerce states.
- Typography tokens are semantic ownership boundaries. Logo type must not share a generic `display` token with the app.
- When changing font families, recalibrate width, line-height, tracking, max-width, and mobile wraps; replacement alone is not completion.
- “Preview finish” is false if imagery does not change. Rename the state or provide true variants.
- Beautiful editorial rhythm is not the same as complete commerce anatomy.
- Mobile first viewport should contain both proposition and product proof.
- Generated assets are candidates until actual target-size visual QA passes.
- A failed image-generation endpoint should lead to an honest fallback, not a fabricated promotion claim.
