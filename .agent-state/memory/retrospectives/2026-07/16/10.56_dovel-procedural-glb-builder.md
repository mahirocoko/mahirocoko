## AI Diary

This session changed my sense of what “real asset production” can mean inside a web repo. I initially treated Blender as the likely threshold for a true model, but the actual product need was narrower and better served by procedural geometry: deterministic meshes, named groups, named materials, and a model whose parts respond directly to the configurator. The first success was functional, but Mahiro’s question about placement forced a more honest review. Arc, Halo, and Pocket were in the correct order, yet the rail itself did not convincingly inhabit the product promise of a desk edge. That distinction—relative placement versus physical truth—was important. I also saw again that generated or programmatic assets cannot be approved by build output. V1 passed the contract and still needed visual comparison. V2 improved only because we used the promoted product renders as bounded evidence, preserved rollback, and reviewed graphite, silver, isolated modules, mobile, reduced motion, and failure states separately. With a +50% weekly session change and a five-day streak, this felt like useful momentum rather than novelty: a new capability earned by one complete accepted proof, while still resisting the temptation to ship a broad skill after a single reuse case.

## Honest Feedback

1. **The first model solved structure before fidelity.** That was appropriate, but the Arc Dock, Halo direction, Pocket Tray depth, and desk contact were visibly approximate. I needed the user’s follow-up question to state clearly that the module order was correct while physical mounting was not final.
2. **The first material pass underestimated metal rendering.** Graphite collapsed toward black because color, metalness, roughness, lights, and background were treated too independently. The fix required tuning the whole reflection/contrast relationship rather than brightening one token.
3. **Evidence capture exposed runtime subtleties.** Asymptotic opacity left ghost modules in 450ms screenshots, and WebGL parent screenshots sometimes composited DOM siblings incorrectly. We had to distinguish actual runtime defects from capture behavior, hard-zero hidden groups, and verify DOM geometry separately.

The session recovered well because each issue became a contract: exact fallback labeling, hard-zero module removal, deterministic model hashing, bounded geometry budgets, and explicit concept-vs-CAD language. We also made the right skill decision: preserve a reusable `web-3d` memory workflow now, but wait for a second real project before creating and releasing a new persistent skill.

## Lessons Learned

- Procedural Three.js plus `GLTFExporter` can produce a real, compact, configurable model without Blender when the target is concept proof rather than CAD.
- Asset contracts should precede visual polish: units, bounds, node/material ownership, deterministic hash, and validator gates.
- Single-view renders are valid silhouette/material references but cannot establish hidden mechanics.
- Review models in the actual product surface and matched V1/V2 camera states, not only as isolated exports.
- Lazy loading, truthful fallback labels, reduced motion, DPR/camera bounds, and semantic controls are part of the 3D asset contract.
- Metal credibility is a coupled lighting/material/background problem.
- Module removal requires an explicit zero/visibility cutoff; opacity alone can leave ghosts.
- Spend bevel/detail geometry only on silhouette-critical surfaces to keep GLB size bounded.
- Do not promote a new skill from one proof when focused project docs plus durable memory are sufficient.
