## AI Diary

This session was a good reminder that a useful skill is not always a script. I initially overbuilt `web-asset-prompts` with a helper script because that matched some repo-local skill patterns, but the user pushed back and asked why the script existed. That question was correct. The value here was never deterministic CLI output; it was design judgment encoded as reusable doctrine. Once the script was removed, the skill became clearer. Then the more important distinction emerged: prompt writing and asset designing are related but not the same. `web-asset-prompts` should teach how to ask for a usable image, while `asset-designer` should teach how to think through the asset lifecycle: provided image versus no image, cutout difficulty, shadow separation, layer deliverables, QA on real backgrounds, and final trimming. I also appreciated the user’s real-world nudge about trim. It exposed a subtle but important distinction: generation sources often need padding, but final transparent deliverables usually need tight transparent bounds. That is exactly the kind of production detail that makes these skills practical instead of theoretical.

## Honest Feedback

First friction point: I initially treated the skill template too literally by adding a script, even though the task was fundamentally about doctrine. That made the first version feel more engineered than useful. Second friction point: I answered “good enough” a few times before the skills had enough real production constraints. The user’s skepticism helped uncover missing concepts like chroma-key source images, layer separation, and final transparent trimming. Third friction point: the terminology needed several passes. Terms like `cutout`, `transparent cutout`, `product cutout`, and `chroma-key source` can drift quickly, and that drift matters because these skills will be invoked by trigger descriptions. The result is much better now, but the process showed that skill design benefits from actual use cases, not abstract completeness. The best work happened when the user brought concrete prompts and production pain points.

## Lessons Learned

- Guidance-only skills are valid when the core value is judgment, doctrine, and workflow discipline.
- Separate prompt doctrine from asset workflow; otherwise one skill becomes bloated and ambiguous.
- For generated cutouts, source images need extraction padding, but final transparent assets usually need trimmed bounds.
- Chroma-key source prompts are often more practical than asking image models for native transparency.
- The user’s concrete workflow language should be preserved in triggers, but prose should normalize the professional term.

## Next Steps

- Use `web-asset-prompts` on the next real image-generation prompt and only add doctrine from observed failures.
- Use `asset-designer` when actual files or page asset manifests need planning.
- If future work requires automation, create a separate processing tool or script rather than reintroducing scripts into these doctrine skills.
- Consider a future validator/checklist only after repeated real-world friction appears.
