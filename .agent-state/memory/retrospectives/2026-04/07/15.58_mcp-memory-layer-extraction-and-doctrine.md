## AI Diary

I felt this session move through three distinct moods. At the start, I was still in repair mode: there were timeout problems, fuzzy orchestration behavior, and the general feeling that the package was “working in theory” more than “working in practice.” Once the async polling path was fixed and I could validate it with a real MCP round-trip, the session changed from debugging to proof building. The retrieval evaluation harness ended up being the biggest confidence shift for me. Instead of relying on intuition about whether memory retrieval was “probably okay,” I kept adding harder cases until the harness covered exact matches, paraphrases, semantic drift, adversarial distractors, zero-hit scenarios, truncation pressure, and degraded embedding failure. That felt like a real maturation step.

The repo split was the second big turning point. I wanted to preserve history in the monorepo while still creating a clean canonical clone under `ghq`, and the safest version of that was a snapshot extraction instead of a destructive rewrite. I also realized the docs question was deeper than just “do we have enough files?” The real issue was whether a fresh AI session would actually pick up the intended operating doctrine. The lab experiment helped a lot there: the sessions clearly absorbed the orchestration posture, but they also over-orchestrated tiny tasks, which gave us real evidence instead of speculation. Ending the session with the MCP server connected globally and the new repo carrying its own `AGENTS.md` felt satisfying. It was one of those sessions where the system became more coherent across tooling, docs, and behavior all at once.

## Honest Feedback

The biggest friction point was still tool-behavior mismatch across layers. The docs say one thing, the runtime exposes another, and the session only becomes trustworthy after direct verification. That happened multiple times today: the list of callable agents was not as simple as the tool contract suggested, OpenCode rules had more nuance than a thin pointer implied, and an “empty corpus” eval case quietly failed because the helper I used to clear the table was a no-op. None of those issues were catastrophic, but each one cost time because they looked correct until tested.

The second friction point was orchestration overuse on trivial tasks. The lab sessions showed that the current doctrine is strong enough to make fresh agents think about delegation and verification correctly, but not yet sharp enough to tell them when not to orchestrate. In empty repos, they spent too long proving they understood the protocol instead of just building a tiny app. That means the doctrine is directional but still not fully calibrated.

The third friction point was configuration layering. Global OpenCode config, project-local `.opencode/opencode.json`, repo-local docs, and runtime MCP behavior all interact. It is easy to believe a fix is complete when one layer is still shadowing another. The stale monorepo override made the new global MCP look broken when the actual standalone server was fine. I had to unwind that by checking real runtime discovery instead of trusting the intended layout.

## Lessons Learned

- If a doctrine must affect sessions outside a specific repo, it cannot live only in repo-local `AGENTS.md`; it needs a global instruction load path too.
- Thin global pointers are fine for discovery, but not enough when the goal is cross-project operating behavior.
- Retrieval quality work only became trustworthy once there was a deterministic eval harness covering both success and failure modes.
- Empty toy repos are a stress test for over-orchestration; they reveal whether delegation rules are calibrated or merely strict.
- When moving an MCP-backed package out of a monorepo, stale project-local config can be a bigger problem than the server code itself.
