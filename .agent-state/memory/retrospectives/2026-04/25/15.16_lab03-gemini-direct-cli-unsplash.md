## Honest Feedback

The first friction point was over-prompting Gemini with a very large composed prompt embedded directly into the tmux command. It worked eventually, but it made the pane noisy and made failures harder to inspect. The second friction point was relying too long on the same Gemini lane after the `WriteFile` schema error and later after the image follow-up stalled. A faster pivot to a fresh, smaller instruction or direct manual patch would have reduced churn. The third friction point was URL handling through tmux. Query strings are fragile when sent through layered shell and pane input, and the malformed `auto=format` URL made Gemini waste time verifying a broken URL. I did recover by verifying URLs myself and patching the file, but I should have anticipated the escaping problem earlier and used plain URLs, a temporary file, or manual editing sooner. The biggest improvement is to treat direct CLI as an executor lane, not a black box: verify ownership, verify filesystem changes, and explain clearly who did what.

## Lessons Learned

- Direct CLI lanes are good for bounded UI generation, but large prompts should be narrowed after the first successful file write.
- If a Gemini lane hits tool schema problems, prefer a fresh session quickly instead of trying repeated recovery inside a potentially unhealthy state.
- URLs with query strings are fragile through `tmux send-keys`; prefer already-escaped prompts, plain image URLs, or direct file patches for precise asset work.
- When a human asks whether the executor did a change, answer by actual file provenance, not by intended workflow.
- Verification must include both URL reachability and final-file inspection; a URL that was verified outside the file still needs to appear correctly escaped in the HTML.
