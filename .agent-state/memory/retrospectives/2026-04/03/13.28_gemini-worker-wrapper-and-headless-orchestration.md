## Session Summary

I first ran a deep `/learn` pass against `google-gemini/gemini-cli`, then narrowed the investigation to `-p`, `-m`, model routing, and whether Gemini could behave as a cheap subordinate worker under orchestration. After confirming that headless mode is a good worker surface but that model choice is not a perfectly hard pin, I studied OpenCode, Oh My OpenAgent, and nearby runtime patterns to decide how callbacks and completion should work. The implementation outcome was a thin host-managed Gemini wrapper inside `apps/mcp-memory-layer` with a dedicated CLI entrypoint, schema-validated stdin, a normalized JSON result envelope, tests, docs, and a final review/fix after Oracle found one real contract bug in the normalization path.

## Key Code Changes

- Added a dedicated worker CLI that reads exactly one JSON payload from stdin and writes exactly one JSON envelope to stdout.
- Isolated Gemini execution behind a single subprocess boundary so the host can stay responsible for orchestration, retries, and notification policy.
- Created a normalized result contract with statuses for success, command failure, invalid JSON, empty output, timeout, spawn error, and invalid input.
- Added tests for the main happy path and the important failure boundaries, including schema-invalid Gemini output.

## Architecture Decisions

- Chose a **host-managed worker** model instead of trying to make `gemini -p` emit native runtime notifications.
- Kept the implementation thin and local to `apps/mcp-memory-layer`, which already has strict TypeScript, Zod schema style, and a small CLI surface.
- Treated `requestedModel` and `reportedModel` as separate values because the Gemini CLI code path shows routing/fallback can change effective model selection downstream.
- Preserved a stable machine-readable stdout contract so a higher-level orchestrator can safely consume the wrapper.

What stood out to me most was the pattern convergence: the closer I looked at OpenCode, OMO, and the Gemini CLI itself, the more obvious it became that the honest path is a wrapper owned by the host, not a magical subprocess that somehow speaks native runtime events. I like that this led to a small, comprehensible implementation rather than a sprawling orchestration layer.

I also noticed a recurring pattern in my own work: I’m most effective when I keep the distinction between “requested behavior” and “guaranteed behavior” sharp. That showed up twice today — first in the `-m` analysis, where the requested model is not the same thing as the final model, and then again in the wrapper review, where Oracle caught that a parse boundary was accidentally blaming the caller for an internal normalization mismatch. I’m glad that review happened before stopping. It reinforced that a clean contract is not just about types compiling; it’s about assigning the right meaning to failures so the next orchestrator layer can trust what it reads.

## Honest Feedback

Three friction points stood out. First, the workspace shape is broad enough that pattern exploration can point toward incubated or study code that looks relevant but is not the right ownership boundary for implementation. I handled that correctly in the end, but it cost attention and should be treated as a recurring risk in this repo. Second, combined shell gather commands are brittle when they mix heredocs and follow-up shell actions; I tripped that exact edge today and had to cleanly rerun the missing pieces. That is small, but it breaks flow more than it should. Third, the implementation review reminded me that passing typecheck and tests is not the same as having a trustworthy contract. The wrong failure label (`invalid_input`) would have been subtle but damaging for a host orchestrator. I need to keep reviewing failure semantics, not just code correctness, whenever I build machine-facing wrappers.

## Lessons Learned

- Host-managed wrappers are the right boundary when a subordinate CLI cannot emit native runtime events.
- `requestedModel` and `reportedModel` should stay separate whenever downstream routing or fallback can change effective behavior.
- Review feedback is especially valuable at contract boundaries because status semantics matter as much as implementation mechanics.
