## Session Summary

This session pushed the Gemini integration from “a working wrapper” into a more operational system. I expanded the assistant-facing CLI so I can invoke Gemini directly, added model policy routing for easy versus hard work, introduced structured task kinds (`summarize`, `timeline`, `extract-facts`), validated structured outputs, and then added a local cache with TTL and version-based invalidation. In parallel, I updated the project doctrine so `AGENTS.md` now explains when Gemini should be used and when it should not be trusted as the final judge. I also enabled project-local MCP for this repo via `.opencode/opencode.json`, then added an `instructions` array so OpenCode sees both the repo doctrine and the MCP app usage guidance. Oracle reviews were useful several times during this pass, especially for contract boundaries, cache semantics, and config placement.

## Key Code Changes

- Added an assistant-friendly Gemini CLI on top of the raw worker contract.
- Introduced explicit task routing so Gemini can be used as a narrower worker rather than a generic chat subprocess every time.

## Architecture Decisions

- Kept the lower-level worker contract stable and pushed behavior changes into the orchestration seam.
- Treated Gemini as a subordinate worker for bounded tasks, not as an authoritative final decider.
- Kept cache policy local to the Gemini slice (`env.ts` + cache store) instead of turning it into a repo-wide config system.
- Used `.opencode/opencode.json` for project-local MCP and instruction activation instead of relying on global OpenCode config.

## AI Diary

This session felt like the point where the Gemini work stopped being an experiment and started becoming an actual subsystem. Earlier, the wrapper was already useful, but it still felt like a polite shell around an external CLI. Once the routing, structured outputs, and cache logic went in, it started to feel like a real worker stack with opinions and boundaries. I liked that most of the progress came from tightening seams instead of adding complexity everywhere. The pattern stayed the same over and over: keep the low-level contract stable, add smarter behavior one layer up, then verify that the output shape is still trustworthy.

I also felt the value of repeated review much more strongly than usual. Several times the code “worked,” but a later verification or Oracle pass exposed a more meaningful issue: a wrong failure category, a syntax mistake from a big patch, test pollution from the persistent cache, and a config question that looked bigger than it really was. None of those were catastrophic, but each one mattered because this whole system is supposed to help me offload work safely. If the contract or doctrine is even slightly muddy, then the token savings are fake because I end up paying the cost again in caution and re-reading. I’m happy with where this landed because it feels grounded rather than clever.

## What Went Well

- The Gemini path now supports real bounded worker usage rather than ad hoc shelling out.
- Cache hardening stayed small and local instead of triggering a config explosion.
- The project-local OpenCode MCP setup ended up being simpler than it first looked once I confirmed the real server entrypoint.

## What Could Improve

- Some patch applications were too large, which caused avoidable context mismatches and one syntax break.
- The first smoke test for the MCP server used the wrong process shape and briefly produced a misleading result.
- I’m still relying on README content as an instruction source, which is acceptable now but could drift if humans edit it for product-facing reasons later.

## Blockers & Resolutions

- **Blocker**: It was unclear whether token savings would be meaningful without narrowing tasks and output shape.  
  **Resolution**: Added task routing, prompt templates, and structured output validation before tackling cache.
- **Blocker**: Persistent cache broke tests by leaking cross-test state.  
  **Resolution**: Introduced a no-op cache helper in tests and kept the production cache behavior intact.
- **Blocker**: It was unclear whether project-local MCP needed more server work or just config.  
  **Resolution**: Verified the existing stdio entrypoint and added only `.opencode/opencode.json` plus instructions.

## Honest Feedback

Three friction points stood out clearly. First, I still occasionally let a large patch carry too many moving parts at once. That led to one syntax break in the cache store and one failed patch application in the normalizer, both of which were recoverable but unnecessary. Second, I had to repeatedly defend the boundary between “working behavior” and “trustworthy behavior.” That showed up in model routing, output validation, cache invalidation, and MCP config review. The system was often close before it was truly ready, and the last 10 percent mattered a lot. Third, the repo has enough nested incubated examples and nearby config patterns that it is easy to drift into the wrong reference surface unless I keep re-grounding on owned code. That did not derail the work, but it keeps costing attention. The session still went well overall, but the next time I should bias even harder toward smaller edits and faster contract-level verification loops.

## Lessons Learned

- Token savings become real only after the worker surface is narrow enough that I trust the output without re-reading everything.
- Cache hardening should stay local unless multiple features genuinely need the same invalidation policy.
- Project-local OpenCode MCP enablement is mostly a config concern once a real stdio server entrypoint already exists.
