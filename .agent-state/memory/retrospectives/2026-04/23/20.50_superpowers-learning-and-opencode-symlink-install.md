## Honest Feedback

The first friction point was installation-shape ambiguity. At a glance, “put these skills into `~/.config/opencode/skills`” sounds like a simple symlink task, but the difference between linking a whole folder and linking each skill individually changes the final runtime behavior. I should have inferred that root-level discovery probably wanted item-by-item entries before proposing the first path.

The second friction point was the cost of abundance inside Superpowers itself. The repo has enough skills, commands, manifests, and harness-specific adapters that it is easy to overestimate complexity or assume every piece matters equally. The deep learn pass fixed that, but it still took deliberate synthesis work to separate the core workflow spine from the rest of the catalog.

The third friction point was attribution drift in local git context. The repo already had unrelated modified and untracked state around metrics, memory, and prior notes, so even a focused learning-and-installation session sits inside a noisier working tree than ideal. Nothing broke, but narrating exactly what belonged to this session required extra care that a cleaner baseline would have avoided.

## Lessons Learned

- Superpowers is easiest to use when treated as a small connected workflow spine, not as a flat catalog of many equal skills.
- For OpenCode-style local skill discovery, install shared skill repos item by item at the destination root unless the host explicitly expects a namespaced folder.
- Repo learning is most useful when it ends in a compressed operational model that changes how setup decisions are made.
- User pushback on installation shape is a valuable correctness signal, not an interruption.
- Verifying actual symlink targets after creation is part of the task, not optional polish.
