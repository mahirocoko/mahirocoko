## AI Diary

Today felt like one of those sessions where the system only became trustworthy after I forced myself to keep cutting away ambiguity. I started from what looked like a fuzzy idea—“make a frontend design skill”—but the actual progress only happened once I separated the repo into its real layers: canonical prompt assets, sandbox experiments, and skill-owned runtime logic. I noticed that the temptation kept showing up in the same form: overpromising too early. It would have been easy to say we already had a design engine, or to pretend the labs proved more than they really did, or to stretch the skill into a general website generator before the underlying contracts were clean. Instead, I kept pulling it back toward explicit boundaries. That was the right move.

I’m especially glad I did not stop after the first implementation pass. The Oracle review caught two small but meaningful flaws, and fixing them made the skill feel more intentional. The relocation of validation from `apps/design-prompts` into the skill itself also mattered more than it first seemed. That change made ownership visible. By the end of the session, I felt the direction become much clearer: the current system is not yet a multi-target generator, but it is now a credible compose-and-validate core. The biggest insight is that the future bottleneck is no longer “how do we build a skill at all?” It is “how do we preserve honest boundaries while evolving from one target to many?” That feels like real progress because it moves the problem from vagueness to architecture.

## Honest Feedback

The biggest friction point was that prompt assets, runtime logic, and sandbox expectations were partially aligned in spirit but not in documentation. I had to repeatedly re-establish what was canonical, what was sandbox-only, and what the skill was actually allowed to own. That meant some time was spent correcting conceptual drift instead of moving straight forward.

The second friction point was that the existing prompt canon is more target-coupled than it first appears. At first glance it looks like a general design prompt library, but once I read the content carefully it became obvious that the shared baseline and many general prompts hard-code HTML/Tailwind assumptions. That makes future multi-target ambitions possible, but not cheap. The coupling lives in data, not just code, which is a more stubborn kind of debt.

The third friction point was workflow confusion caused by good intentions landing in the wrong place. The validation harness was useful, but when it first lived under `apps/design-prompts` it blurred the boundary between sandbox artifacts and skill-owned logic. Likewise, `lab02` looked promising, but it immediately raised questions about whether it was a validated result, a prompt package, or merely another sandbox input set. None of these were fatal problems, but they showed that direction clarity is now the main thing we have to protect. The session succeeded because I kept treating naming, location, and ownership as architectural decisions rather than cleanup chores.

## Lessons Learned

- A thin skill wrapper plus a deterministic script is the right first shape for this repo.
- Validation belongs with the skill that owns the runtime contract, not with sandbox inputs.
- `lab02` can be more aligned than `lab01` without becoming canonical; “better aligned” is not the same thing as “source of truth.”
- The main blocker to multi-target evolution is canonical prompt-data coupling, especially the embedded HTML/Tailwind output contract.
- Before adding framework targets, the system needs a target-contract layer that keeps shared design intent separate from output/runtime assumptions.
