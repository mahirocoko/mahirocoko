## Honest Feedback
First friction point: worker execution still has an annoying gap between “good thinking” and “reliable direct application.” Opus produced high-quality routing and wording advice, but repeated timeouts made it harder than it should be to let the worker fully own the edit. That introduces an awkward handoff where I still need to be the patch applicator even when the reasoning has already been delegated correctly. It is workable, but it is not yet smooth.

Second friction point: local doctrine can become stale faster than tool capability changes. The repo had a rule shape that once made sense, but it had quietly become misleading. That kind of drift is dangerous because it changes behavior invisibly. The user had to push on it for the mismatch to surface. I should be more proactive about revalidating routing rules against actual model capability, especially when a model upgrade materially changes what is safe or sensible.

Third friction point: product assessment and policy editing can sprawl if I do not force them into durable artifacts quickly. It is easy to leave good reasoning in chat messages. Writing `MARU_REALTIME_PRODUCT_REVIEW.md` and updating `AGENTS.md` fixed that, but I felt how easily the session could have stopped at discussion. The lesson is to convert opinion into repo state faster when the user is clearly steering toward doctrine or product judgment.

## Lessons Learned
- Routing policy should describe task shape, not ossified assumptions about a model family.
- `gemini-3.1-pro-preview` belongs in the lane for design-led UX/UI implementation, not only UI critique.
- `gemini-3-flash-preview` is best framed as a low-level, cheap, repetitive, hotfix-oriented worker.
- Cursor should be described as a broad engineering worker across backend, frontend, refactors, and multi-module implementation.
- Product reviews become materially more useful once they are turned into root-level markdown artifacts rather than left as chat summaries.
