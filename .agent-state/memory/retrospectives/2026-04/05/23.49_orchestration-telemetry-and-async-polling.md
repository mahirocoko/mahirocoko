## Timeline
- ตรวจ root cause ของ `Request timed out` และยืนยันจาก trace ว่า workflow ฝั่ง orchestration จบจริง แต่ client timeout ตอนรอ response
- เพิ่ม `waitForCompletion: false` และ `get_orchestration_result` เพื่อให้ long-running orchestration ตอบกลับเร็วและ poll ผลทีหลังได้
- ใช้ flow ใหม่เรียก Opus วิเคราะห์ `apps/blue-ledger` และยืนยันว่า async path ใช้งานได้จริง
- หยุดจากงาน app analysis แล้ว pivot กลับมาที่ orchestration telemetry ตาม feedback ของผู้ใช้
- วิเคราะห์จากโค้ดและจาก Opus ว่าควรทำ data quality ก่อน dashboard โดยเฉพาะ per-job status
- เพิ่ม `status` ลงใน `jobModels`, ขยาย `--format usage` ให้เห็น `bySource`, `byWorkflowStatus`, `byJobStatus`, `byDay`, `workflowOutcome`, `jobOutcome`, `byRequestedModelOutcome`
- เจอ regression กับ legacy traces ที่ไม่มี `jobModels.status` แล้วแก้ fallback ไม่ให้สรุปผลผิดเป็น `undefined`
- ต่อรอบสอง: เพิ่มการเก็บ `runner_failed` ลง trace, เพิ่มตัวกรอง `--from-date` และ `--to-date`, แล้วแก้ date-only filter ให้ตีความเป็นทั้งวัน
- ปิดท้ายด้วย targeted tests, typecheck, และเช็ก output จริงของ `list-orchestration-traces --format usage`

## Honest Feedback
มีสามจุดที่ผมรู้สึกติดขัดชัดเจนใน session นี้ อย่างแรกคือ state ของงาน orchestration ใน repo ตอนนี้ยังมีสองแนวคิดปะปนกันอยู่: append-only trace สำหรับ analytics กับ per-request result store สำหรับ polling มันใช้งานได้ แต่ภายในหัวต้องคอยจำตลอดว่าอะไรคือ source of truth ของคำถามแต่ละแบบ ซึ่งทำให้ reasoning cost สูงกว่าที่ควรเป็น อย่างที่สองคือ test surface ของระบบค่อนข้างกว้าง พอแตะ trace format, CLI filters, usage summary, MCP register tools และ legacy compatibility พร้อมกัน ผมต้องไล่ปิด regression ทีละจุด แม้ทั้งหมดจะเล็ก แต่รวมกันแล้วทำให้ flow ขาดความต่อเนื่อง อย่างที่สามคือ tooling ของ error formatting ระหว่าง parser กับ tests ยังไม่คงเส้นคงวา เช่นข้อความจาก Zod กับข้อความที่เราอยากให้ CLI-level test จับ ทำให้ต้องผ่อน assertion ให้ยึดสาระมากกว่ารูปแบบ ซึ่งสะท้อนว่าขอบระหว่าง validation layer กับ user-facing CLI layer ยังไม่ชัดเท่าที่ควร ถ้าจะทำงานพวก observability ต่อ ผมควรผลักดันให้ boundaries พวกนี้คมขึ้นก่อน ไม่งั้นเวลาเพิ่ม metric ใหม่จะต้องมาเสียเวลาซ่อมขอบระบบตลอด

## Lessons Learned
- การมี `requestedModel` และ `reportedModel` อย่างเดียวไม่พอสำหรับวิเคราะห์ orchestration; ต้องมี per-job `status` ด้วยจึงจะ derive reliability ได้จริง
- Legacy trace compatibility ควรถูกออกแบบเป็น explicit fallback ไม่ใช่ปล่อยให้สรุปผลออกมาเป็น `undefined` แล้วค่อยตามแก้ทีหลัง
- Date filter แบบรับทั้ง ISO และ date-only ต้อง define semantics ให้ชัดตั้งแต่ต้น มิฉะนั้นผู้ใช้จะตีความไม่ตรงกับ implementation
