## AI Diary

I felt the session shift from “make the skill useful here” to “make the skill able to travel,” and that was the right correction. My first implementation earlier in the day had treated project-local references as acceptable because they were nearby and useful, but the user caught the deeper product boundary: a skill that wants to become portable cannot depend on app sandboxes or repo-level prompt folders. The cleanest move was not to add more logic. It was to move true runtime data into the skill, reduce scraped or app-local material into small non-canonical examples, and make the script resolve from the skill bundle. I also had to keep reminding myself not to overbuild. The dangerous move would have been creating a clever reference loader or extractor. The better move was boring and durable: resource folders, clear wording, validation fixtures, and a Thai user-facing doc. With a +87.5% weekly session change and a 6-day streak in the pulse data, the project has a lot of momentum, but momentum can easily become sprawl. This pass helped turn that energy into boundaries instead of more surface area.

## Honest Feedback

Three friction points stood out. First, the work had accumulated many related changes across skill docs, resources, archived handoffs, memory notes, and validation files, which makes final review harder than it needs to be. The changes are coherent, but the commit boundary will need careful attention. Second, copying the full prompt JSON into `frontend-design` creates a new maintenance concern: there are now two places that may look canonical unless the team decides which source owns future updates. The current skill-owned copy is necessary for portability, but it should be treated deliberately. Third, I initially leaned on direct grep for fast inspection despite the orchestration bias toward delegated exploration. It was effective for exact path checks, but it is still a reminder to keep tool choices intentional. The best part of the session was that the user’s portability constraint stayed concrete and prevented me from drifting into unnecessary script intelligence.

## Lessons Learned

- Portable skills should own the references and runtime resources they require.
- Project-local examples are acceptable during incubation, but they should become bundled excerpts or placeholders before a skill is expected to travel.
- `frontend-design` should keep scripts deterministic and put design judgment in Markdown resources.
- `asset-designer` is stronger as an asset director than as a per-image prompt writer.
- Thai external docs are useful for turning internal skill boundaries into a shareable operating model.
