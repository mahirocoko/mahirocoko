## Key Code Changes
- Rebased the shared UI layer around shadcn-inspired primitives without `forwardRef`, while keeping the repo’s React 19 posture.
- Introduced `field`, `sheet`, `alert-dialog`, and `sidebar` primitives to support denser product UX.
- Added single-document `members[]` support and board operations for members and columns.
- Implemented a searchable owner picker and manager sheets for editing assignees and columns.
- Fixed a realtime hydration loop by stabilizing effect inputs in `use-pulselane`.
- Locked dependency versions and validated compatibility with stricter React hook lint rules.

## Architecture Decisions
- Keep members inside the board document for now instead of introducing a second Maru document.
- Reuse shadcn structural patterns where they improve consistency, but keep them adapted to the repo’s React 19 + local token system.
- Prefer incremental shell migration over a giant rewrite: first custom sidebar, then real sheets, then sidebar block structure.
- Use confirm dialogs only for destructive actions that meaningfully affect the user’s board state.

## AI Diary
I spent this session in the mode where a small app stops being “just a board demo” and starts needing product judgment on almost every change. At first the work looked straightforward: align some UI files, swap in a few shadcn patterns, lock dependencies, and clean up the file tree. But once I got into it, every improvement exposed the next layer of inconsistency. The first thing that really changed the session was noticing the hydration loop. That bug made the whole app feel unstable, and fixing it re-centered the work around trustworthy state flow instead of cosmetic polish. After that, I kept pushing because the user clearly wanted more than cosmetic cleanup. They wanted something that felt structurally correct.

I also felt the tension between “match shadcn” and “stay honest about what we are actually doing.” The combobox situation was a good example: the docs surface and the current implementation reality had diverged, and I had to stop pretending they were the same thing. That forced better decisions. The same happened with the sidebar. I initially improved it visually, but the user was right that it still was not the real block shape. I had to go back, admit that, and finish the migration properly. That honesty made the later result better. Even with the low pulse metrics snapshot for today, this felt like a high-leverage session because it turned a scattered set of half-patterns into a cleaner, more coherent shell that I would trust as a base for future feature work.

## What Went Well
- The work stayed grounded in the actual repo state instead of assumptions.
- Verification stayed tight; repeated `build`, `test`, and `lint` runs prevented false confidence.
- The user’s corrections improved the result materially, especially around shadcn interpretation and sidebar expectations.
- The single-document members approach kept complexity under control while still enabling useful UX.

## What Could Improve
- The first pass on combobox and sidebar overclaimed alignment with upstream patterns before the implementation actually matched them.
- I should have recognized the missing animation utility problem earlier instead of letting sheet transition debugging drag.
- The UX passes would have been smoother if I had introduced better confirm and shell primitives sooner rather than incrementally discovering the need for them.

## Blockers & Resolutions
- Gemini repeatedly failed with capacity errors. I switched to Cursor for guidance and used upstream source references directly when needed.
- macOS case-only rename behavior created git/index confusion. I resolved it with explicit `git mv` through temporary names.
- React 19 hook lint rules surfaced effect-state issues. I adjusted the hooks rather than downgrading dependencies.
- Missing animation utility support broke shadcn-like transition classes. I replaced those with supported opacity/transform transitions.

## Honest Feedback
The biggest friction point was overconfidence in pattern matching. I initially treated “shadcn-like” as close enough in places where the user specifically cared about the real source shape and architectural intent. That created extra churn because I had to revisit combobox, sheet behavior, and the sidebar after the user correctly called out that the work was still half-done. I should have trusted the request more literally from the start and anchored sooner to the actual upstream source instead of local approximation.

The second friction point was tool reliability. Gemini failing repeatedly with capacity issues disrupted momentum, and some of the async worker interfaces were good enough for guidance but not good enough for dependable end-to-end execution. I adapted, but the session lost time every time I had to switch mental models between delegation, local implementation, and verification. I can handle that, but it still adds drag when the task is already architecture-heavy.

The third friction point was the cumulative nature of UX debt. A header that felt a little awkward, a sidebar that looked okay but was structurally wrong, custom sheets with non-working transitions, and missing confirm flows were all individually survivable. Together they made the app feel more unfinished than the code alone suggested. The good news is that each of those issues was fixable, but the lesson is that product-shell inconsistencies compound quickly. Leaving them half-solved costs more than finishing them in one deliberate pass.

## Lessons Learned
- If the human asks for a specific upstream pattern, match the structure honestly, not approximately.
- For Tailwind v4, animation assumptions need explicit verification; shadcn-like class names are not enough by themselves.
- A single-document approach can carry farther than expected if the scope is intentionally narrow and the operations are clear.
- Product-shell work benefits from finishing the interaction stack together: layout, dialogs, confirms, and navigation should not be treated as isolated details.

## Next Steps

- Add visual and interaction tests for manager sheets and sidebar behavior if this shell continues to evolve.
- Only after that, move on to genuinely new product features rather than more structural cleanup.
