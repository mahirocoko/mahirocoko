## Honest Feedback
First friction point: I had to resist the temptation to over-formalize the imported guidance. The external repo uses neat, memorable principles, and it would have been easy to paste them almost verbatim. That would have been lazy synthesis rather than good policy editing. Second friction point: the surrounding instruction environment is already dense. There are repo rules, local rules, orchestration rules, and skill-specific rules. Any addition to `~/.claude/CLAUDE.md` risks becoming prompt dilution if it does not earn its place. I had to keep trimming the wording until it matched the file’s existing voice. Third friction point: the actual file I changed lives outside the current git repo, which means normal repository verification signals are weaker. I could still read the file and verify the wording directly, but the session had less of the usual git-based closure. I think the outcome is good, but I should stay alert when policy work happens across repo boundaries because it is easier to create drift and harder to audit later.

## Lessons Learned
- Behavioral guidance should be merged by function, not by origin. Popular external guidance is only useful if it fills a real gap in the local doctrine.
- Reliability rules and execution rules reinforce each other, but they should stay visually separate so the model can preserve the distinction.
- Small instruction-file edits benefit from outside review just as much as code changes do, especially when the risk is conceptual drift rather than syntax mistakes.
