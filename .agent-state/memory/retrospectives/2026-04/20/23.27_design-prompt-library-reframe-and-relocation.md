## AI Diary

I felt this session tighten itself by degrees rather than by one big clever move. At the start, the work looked almost done because the JSON had already been rebuilt and documented, but the naming kept nagging at me. The more I read the actual contents, the less honest the `opencode` label felt. The files were full of design direction, layout patterns, animation language, styling systems, and WebGL guidance. Calling them `opencode` prompts was not exactly false, but it was downstream-context naming, not content-first naming. I’ve learned that this kind of small mismatch becomes surprisingly expensive because once docs, filenames, and folder structure disagree, every later explanation becomes muddy.

I also felt the cost of moving carefully in a live repo. Even a documentation-heavy task has edges: broken links, stale paths, duplicate terminology, and the temptation to stop at “good enough” after the first successful pass. The Oracle review helped here, not because it found something catastrophic, but because it confirmed that the remaining discomfort was real and specific. The final rename to `design-*` felt cleaner, more truthful, and more reusable beyond a single tool context. I’m ending the session feeling calmer than I started, mostly because the repo shape now says the same thing the content says.

## Honest Feedback

Three friction points stood out clearly. First, I tripped over the exact heredoc parsing edge case that the `rrr` skill warns about. That was avoidable, and it reminded me that following an instruction mechanically is not the same as internalizing its failure modes. Second, the repo has enough nested `.agent-state` content that broad searches can hit loops or noisy paths, which keeps turning simple discovery into something that needs more deliberate scoping than it should. Third, the work took multiple passes because I initially accepted the integration-facing `opencode` framing too quickly, then had to revisit it once the user pointed out that the content itself was broader.

The deeper lesson in that friction is that I still sometimes optimize for the first coherent label instead of the truest label. The initial docs were not bad, but they carried a subtle conceptual debt that the user spotted immediately. I also notice that verification is strongest when I keep it concrete: parse the JSON, count entries, verify old names are gone, verify links point locally, and then ask Oracle for a final structural read. When I do that, the work feels grounded. When I don’t, I start narrating confidence too early.

## Lessons Learned

- Name artifact bundles after what they contain, not only after one consumer that may use them.
- When content and docs belong together conceptually, co-locating them reduces ambiguity and makes the source-of-truth posture easier to defend.
- Validation for docs-and-data moves should include path checks, parse checks, stale-name checks, and reference checks, not just visual inspection.
- A review agent is especially useful for catching conceptual mismatch after the implementation already looks technically correct.
