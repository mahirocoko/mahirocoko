I hit at least three meaningful friction points today. First, I still had too much internal inertia around using workers “enough.” Even after the repo rules clearly leaned toward delegation, I kept drifting back to local analysis as the default. That was not a tooling failure; it was a posture failure. The user had to call it out explicitly, and I needed that correction. Second, the package-local worker commands and root-repo expectations were easy to blur together. I initially tried invoking wrapper behavior from the wrong layer, which exposed that my mental map of where orchestration commands actually live was still too fuzzy. Third, I let some documentation drift into over-specific guidance, especially around Cursor planning and Opus. That came from trying to simplify guidance too aggressively, and it flattened an important distinction between choosing a strong model and deciding whether a planning mode is needed at all.

There was also some avoidable churn in the verification loop. A few times I had to patch tests after discovering that the implementation was correct but the expectation was sloppy or time-sensitive. That is not catastrophic, but it is still noise. The upside is that I did respond well to feedback loops once they appeared: I tightened the tests, reran the package, and kept asking Oracle for a skeptical pass instead of defending the first version. Still, the best version of this session would have made those distinctions earlier and with fewer corrections. The key criticism is simple: I was directionally right on most topics, but I only became operationally precise after being challenged. I want the next session to start from that sharper posture rather than needing to rediscover it mid-stream.

## Lessons Learned
- In this repo, worker-first is not just a preference; it is the intended operating model, and direct reads should mostly serve prompt grounding and targeted verification.
- `mode` and `model` are separate decisions. A strong planning model does not imply that `--mode plan` should be enabled by default.
- Runtime failures are the best prioritization signal for wrapper hardening. The fenced-JSON Gemini issue was a better anchor than any speculative cleanup list.
- Retrieval modes should not be decorative. If an API exposes them, they should affect ranking, context building, or cost behavior in a visible way.
- Degraded behavior is not finished until it is observable. Returning `degraded: true` was good; proving it persisted in traces was better.
