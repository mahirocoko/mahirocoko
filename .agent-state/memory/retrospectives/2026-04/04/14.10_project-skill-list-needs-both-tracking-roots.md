## Honest Feedback

Three friction points stood out. First, the original `project` skill source was too minimal to act as a reliable executable instruction set. It described intent, but not enough operational detail, so wrapper behavior could easily collapse into an incomplete fallback path like “read `.origins` and stop.” Second, nested-repo work still adds cognitive overhead every time. I had to keep switching between the outer repo, the incubated `mahiro-skills` repo, and the installed `.opencode` result, and that kind of root juggling is exactly where subtle release mistakes usually happen. Third, the release surfaces were slightly out of sync before I touched them: package version, README examples, install script examples, and tests were not all anchored to the same patch version. None of this was disastrous, but it reinforces a pattern I should keep respecting: when a packaged skill changes, the behavior doc, release references, tests, install path, and installed output all need to move together or the next human will trip over stale truth.

## Lessons Learned

- A tracked-project listing is incomplete unless it reads both `learn` and `incubate` roots by default.
- Thin skill descriptions are dangerous when command wrappers depend on them as executable guidance.
- Release alignment includes docs and tests, not just version numbers and tags.
- Nested repo workflows stay safe only when each path boundary is named and verified explicitly.
