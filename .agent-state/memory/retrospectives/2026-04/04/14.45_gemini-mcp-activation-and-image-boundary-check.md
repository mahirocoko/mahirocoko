# Session Retrospective

## Session Summary

This session turned the Gemini worker work from “implemented in code” into “usable in the project runtime.” I verified the assistant-facing Gemini path against real calls, set the default model policy to match the intended easy-versus-hard split, added task routing and structured outputs, hardened caching with TTL and versioning, and wired both OpenCode and Gemini CLI to the local MCP memory server through project-local config. I also pushed further on the question of image generation. That part was valuable because it clarified the real boundary: the headless Gemini worker can carry text and artifact references, but it is not a reliable binary-image transport. I implemented an MCP-backed image-task path, verified it, then rolled it back when the runtime experiment showed that the actual Gemini environment still lacked a usable media-generation MCP tool and the result shape was not worth keeping half-ready.

## Timeline

- Confirmed the Gemini worker could be called directly through the assistant-facing `bun run gemini -- ...` path.
- Added model policy so normal work uses `gemini-3-flash-preview` and hard work uses `gemini-3.1-pro-preview`.
- Added task routing for `summarize`, `timeline`, and `extract-facts`, then validated structured outputs for those bounded task kinds.
- Added local cache behavior, then hardened it with TTL and cache versioning so repeated requests could safely reuse results.
- Updated `AGENTS.md` so the repo doctrine now states when Gemini should be used and how it should be trusted.
- Added project-local OpenCode MCP config and then project-local Gemini CLI `.gemini/settings.json` so the local MCP memory server is visible from both toolchains.
- Verified Gemini could see the project-local MCP server by asking it to list MCP tools.
- Investigated native image generation in `gemini-cli`, implemented an MCP-backed image task, tested it, then rolled the uncommitted image-task slice back after runtime evidence showed the environment did not yet have a valid media-generation MCP tool.

## AI Diary

I felt unusually satisfied with the way this session stayed grounded in runtime truth instead of getting trapped in abstraction. The Gemini worker work could easily have become a never-ending architecture exercise, but each layer only earned its place when it could survive an actual check: run the worker, inspect the model behavior, look at the output contract, see whether MCP is actually visible, and then decide the next move. That pattern made the whole thing feel less magical and more trustworthy. I liked that the project-local MCP activation ended up being simpler than it first appeared. Once I confirmed the local stdio server already existed, the rest of the work was mostly about putting the right config in the right place and making sure doctrine matched behavior.

The image-task exploration was more emotionally mixed. Part of me wanted to keep the new `image` task because the design was clean and the reviews were positive. But the runtime test was the important reality check: a well-designed boundary is still not the same thing as an actually available capability. Rolling it back felt correct, but it also reminded me that I still have a bias toward carrying promising abstractions a little farther than the current environment deserves. The good part is that the rollback happened before the half-ready path became part of the stable system. That feels like a small but real sign of discipline.

## Honest Feedback

Three friction points stood out. First, there was a lot of context switching between implementation, runtime validation, config doctrine, and repo-local tool activation. None of those tasks were individually confusing, but the switching cost was real and made it easier for small mistakes to creep in. Second, the image-task experiment consumed more attention than its final value justified because the design was sound while the runtime capability was not. That is exactly the kind of situation where it becomes tempting to over-invest in the elegance of a path that is still blocked by environment reality. Third, the worktree already had unrelated changes and historical noise around local state, incubated repos, and notes. I navigated it safely, but it still takes effort each time to separate “what belongs to this task” from “what merely exists nearby.” I should keep biasing even harder toward early runtime checks when a feature depends on external tool capability.

## Lessons Learned

- Project-local MCP activation is usually a configuration-and-doctrine problem once a valid stdio server already exists.
- Gemini worker boundaries become trustworthy when they are validated against the actual runtime, not just against types and tests.
- Image generation for the current worker should be treated as MCP-dependent artifact orchestration, not assumed native capability.

## Next Steps

- Keep using the current Gemini worker stack for text tasks and MCP-assisted memory work.
- If image generation matters later, start by installing or enabling a real media-generation MCP tool in Gemini CLI before reintroducing any worker-side image task.
- Consider one small parser hardening later for Gemini responses that wrap JSON in fenced code blocks.
