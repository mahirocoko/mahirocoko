## AI Diary
I felt more confident here after the statusline debugging because I had just been reminded not to trust assumptions about Letta's hook shape. The tempting answer was “RTK now supports hooks, just run `rtk init` and delete our custom script,” but the actual evidence was more nuanced. RTK's hook layer is good: `rtk hook claude`, `rtk rewrite`, permission-aware exit codes, updatedInput output, and broad agent docs are all real improvements. But Letta's main shell tool is not exactly Claude Code's `Bash`; in this environment it uses `exec_command` and a `cmd` key. That one field name is enough to make upstream `rtk hook claude` silently do nothing. I was glad Mahiro explicitly asked me to test with real `git status`, because my first config edit looked correct on paper but did not actually apply in the running session. The old hook path being cached was another practical lesson: cleanup must be staged, not just deletion. The compatibility shim feels slightly inelegant, but it is the right local bridge until upstream RTK has `--agent letta`. The real win is that the workflow now behaves transparently: raw-looking `git status` returns RTK compact output, while `RTK_DISABLED=1` still gives exact raw output.

## Honest Feedback
There were three friction points. First, I initially treated removing `rtk-suggest-heavy.py` as pure cleanup, but Letta can keep already-loaded hook paths alive until reload or possibly until a fresh session. Deleting the file made old cached references fail rather than gracefully migrate. A safer migration pattern is to replace old hooks with compatibility shims first, then remove them only after a later session proves no cached references remain. Second, I should have tested with a real tool call earlier. Manual payload tests showed the adapter logic worked, but they did not prove that Letta's hook loader was actually invoking the new settings. The decisive evidence was only the real `git status` output. Third, I had to distinguish three layers more explicitly: upstream RTK capability, Letta hook runtime behavior, and this current session's cached hook state. Collapsing those layers makes it easy to say “configured” when the live runtime is still not using it. The final state is good, but the path reinforced that local hook work needs both unit-style payload tests and real command tests.

## Lessons Learned
- Upstream RTK 0.42.4 has solid hook machinery but no first-class Letta target yet.
- Letta `exec_command` uses `tool_input.cmd`; Claude-style RTK hooks handle `tool_input.command`, so Letta needs a thin adapter until RTK supports `--agent letta`.
- Letta 0.27.18 applies `hookSpecificOutput.updatedInput` to tool args, so transparent rewrite is possible; deny-with-suggestion is no longer necessary for this flow.
- Never delete a replaced hook path immediately if the current Letta session might still have it cached. Convert it to an exit-open shim or delegating shim first.
- Validate hook migrations with real commands and an escape-hatch comparison: `git status` should compact, `RTK_DISABLED=1 git status` should stay raw.

## Next Steps
- Keep `rtk-suggest-heavy.py` as a compatibility shim for now; remove it only after a future fresh session confirms no references remain.
- Consider upstreaming a small RTK PR for `--agent letta` / `rtk hook letta` that reads both `cmd` and `command`.
- If repeated, add a small test fixture or script for Letta hook payloads to avoid manual JSON smoke tests.
