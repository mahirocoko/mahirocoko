## Key Code Changes

- Added a `READ_COMMAND_BASENAMES` context for commands that actually read or dump file contents (`cat`, `sed`, `grep`, `rg`, `less`, `head`, `tail`, etc.).
- Added `SHELL_COMMAND_SEPARATORS` and simple command-position tracking so the hook can distinguish command words from arguments.
- Added `token_looks_pathlike()` so path-like secret targets remain blocked even outside read-command context.
- Changed `command_reads_sensitive_path()` to run `strip_heredoc_bodies(command)` before tokenizing shell text, avoiding prompt/script data being treated as shell arguments.
- Added an early `return 0` after shell-command scanning so the fallback direct-argument scan does not inspect the entire shell command string.
- Preserved the guardrail for real secret reads: `cat identity` still blocks.

## Architecture Decisions

- Keep the hook conservative for path-like sensitive material: `.env`, SSH private keys, provider credential paths, and credential/key filenames should still block when they appear as shell path arguments.
- Loosen only the ambiguous bare-word case. A word such as `identity` is too common in design/product prompts, so it should not block unless it is used as an argument to a read-like command.
- Treat the generic fallback as a direct tool-argument guard, not a second pass over already-parsed shell commands. Shell commands need shell-aware parsing; raw fallback scanning is too broad for heredoc-heavy workflows.
- Avoid making prompt authors rewrite normal language around hook limitations. The guard should understand shell structure well enough not to penalize ordinary prose in heredocs.

## Honest Feedback

Three friction points are worth recording. First, the hook’s original mental model was too token-based: it treated all command text as shell syntax, even though heredocs are often data payloads for prompts, generated files, or scripts. That is a classic false-positive source for coding agents because we write lots of text through shell tools. Second, my first fix was incomplete because I looked at `command_reads_sensitive_path()` but not enough at the later fallback in `main()`. The failed retrospective write exposed that gap, and it is a reminder to audit the whole control flow when editing guardrails. Third, the verification is still narrow. It proves the reported problem is fixed and the obvious dangerous case remains blocked, but it is not a full regression suite. A future hardening pass should convert these manual JSON hook invocations into a tiny test file so changes to the guard are less risky.

## Lessons Learned

- Secret-read hooks should parse shell structure, not raw prose payloads.
- Heredoc bodies are data and should usually be stripped before scanning for shell-level hazards.
- Bare words that overlap with sensitive filenames need command-context checks; path-like values are much safer to treat as high-confidence secrets.
- For shell tools, do not run generic direct-argument fallback scans over the entire command string after shell-aware parsing.
- When a guard is over-triggering, patch using a method that avoids triggering the same guard until the fix is installed.
