# Lesson Learned

When auditing a third-party repo like `olore`, the right output is not a dramatic claim that the project is either safe or unsafe. The right output is a concrete map of its boundaries: what network endpoints it talks to, what filesystem locations it writes to, what global directories it modifies, and whether it executes shell commands or privileged flows. `olore` looks materially safer because its CLI runtime does not appear to spawn shell commands, and it verifies package checksums before extraction, but it still downloads artifacts from the network and writes into global agent skill directories and `~/.olore`. That means the repo should be treated as medium-risk operational tooling: understandable, inspectable, and probably fine to test, but not something to install blindly without a sandbox mindset. The broader pattern is durable: trust grows from explicit blast-radius analysis, not from vibes, branding, or documentation polish.
