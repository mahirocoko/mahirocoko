## Key takeaways

- The creator argues AI stock selection is moving from rule-based screeners toward reasoning agents that can apply a personal investing philosophy.
- The system creates a standalone AI “fund manager” agent, Nick, trained on the creator's knowledge base: YouTube transcripts, articles, earnings transcripts, research, and team outputs.
- Nick is intentionally separated from the creator's real portfolio to reduce confirmation bias; it can read the research universe but should not know current holdings.
- The portfolio starts as a paper portfolio with rules: buy-and-hold style, 3-10 positions, max 40% cash, no daily noise, weekly portfolio review, quarterly thesis checks after earnings.
- Every position should have Q conditions / kill conditions: facts that would weaken or invalidate the thesis.
- The agent keeps a markdown memory/mistake log so it can learn from bad theses over time.
- The early portfolio outperformed S&P/Nasdaq over only three weeks; the creator explicitly frames this as an experiment, not investment advice.

## Apply to Mahiro Code

### What is interesting for us
- This is less about “AI chooses stocks” and more about **agent as taste/philosophy executor**: the agent reads a growing knowledge base, applies durable rules, and reports decisions with reasons.
- The most transferable pattern is **decision memory**: record thesis, conditions, actions, and later mistakes in plain markdown so future agent behavior can improve.
- The bias-control idea is strong: do not leak the human's preferred answer/portfolio when asking an agent for independent judgment.
- The cadence is sensible: avoid noisy daily checks; use weekly review for state and quarterly/event-driven review for thesis validation.

### Possible Mahiro workflow adaptation
1. **Define a role-local playbook** before giving an agent autonomy: objective, style, forbidden shortcuts, review cadence, and “I don't know” policy.
2. **Require thesis + kill conditions** for important recommendations, not just a final answer.
3. **Keep agent mistake memory** in a focused markdown file: what it decided, what happened, why it was wrong/right, what future behavior changes.
4. **Separate source universe from answer bias**: give the agent data and constraints, but avoid telling it the answer we hope to hear.
5. **Use event-based reviews** for important domains: after build failures, production incidents, repo convention corrections, or user feedback.

### Candidate actions
- Add a future lightweight “decision log” template for agentic recommendations:
  - decision / context / evidence / alternatives / kill conditions / review date / postmortem.
- For code/research work, ask for “what would falsify this recommendation?” when stakes are non-trivial.
- Consider a small `agent-mistakes.md` or per-project retrospective pattern only if current retrospectives are not enough; avoid duplicating memory layers too early.

### Cautions
- Three-week portfolio performance is not meaningful evidence; treat the clip as workflow inspiration, not investment proof.
- A personalized knowledge base can amplify existing bias. The “hide real holdings/preferences” pattern is important if we want independent critique.
- Financial agents need stricter verification, auditability, and risk controls than ordinary writing/coding assistants.
